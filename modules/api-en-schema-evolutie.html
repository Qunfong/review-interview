Module 7 · D7 Microservices

API- en schema-evolutie

Een veld hernoemen is in je eigen code één refactoring. Op een topic, in een publieke API of in een tabel die oude pods nog lezen, is het een migratie met consumers die je niet kent. Zo gaan uitbetalingen met een lege referentie naar de ledger, en zo valt een rolling deploy halverwege om.

Tijd 45 minStack Java 25 · Spring Boot 4.1 (Framework 7, Jackson 3) · Flyway · KafkaBouwt op modules 3, 5 en 6b

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Een consumer met Jackson 3 krijgt een bericht met een veld dat zijn record niet kent. Exception of niet?
  2. Flyway draait bij het opstarten van de eerste nieuwe pod. Welke versie van je applicatie draait er op dat moment nog tegen de database?
  3. Je voegt PARTIALLY_CAPTURED toe aan een enum die in een event zit. Wie merkt dat als eerste, en hoe?

Wat er onder de motorkap gebeurt

Een contract heeft twee kanten die onafhankelijk deployen. Dat is de hele oorzaak. Er is geen moment waarop "alles tegelijk" de nieuwe versie draait:

  • Rolling deploy. Minutenlang draaien oude en nieuwe pods naast elkaar, tegen dezelfde database en hetzelfde topic. Bij een rollback draait de oude versie weer tegen alles wat de nieuwe heeft achtergelaten.
  • Berichten leven langer dan code. Een topic met zeven dagen retentie bevat berichten van de vorige drie releases. Een nieuwe consumer die opnieuw leest (replay, een nieuwe consumer group, een DLT die opnieuw wordt verwerkt) krijgt oude berichten.
  • Consumers die je niet kent. Merchants die je publieke API aanroepen, het team van de ledger dat je topic leest, een BI-job die rechtstreeks je tabel leest, Debezium op je outbox. Ze deployen in hun eigen tempo, of nooit.

Daarom moet elke wijziging in twee richtingen werken. Backward compatible: een nieuwe lezer kan oude data lezen (oude berichten, oude rijen). Forward compatible: een oude lezer kan nieuwe data lezen. Een Schema Registry noemt dat BACKWARD en FORWARD, en de volgorde volgt eruit: bij alleen backward deploy je eerst de consumers, bij alleen forward eerst de producers. Wil je je over volgorde geen zorgen maken, dan moet de wijziging beide zijn.

Tolerant reader, en wat Jackson 3 daaraan veranderde

De verdediging aan de lezende kant is een tolerant reader: lees alleen de velden die je nodig hebt en negeer de rest. Jackson 3 doet dat nu standaard: DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES staat uit (in Jackson 2 stond hij aan, al zette Spring Boot hem daar zelf al uit). Dat maakt toevoegen veilig. Het maakt hernoemen en weghalen gevaarlijker: wat vroeger een UnrecognizedPropertyException was, is nu een veld dat stil null wordt.

Het databaseschema is ook een contract

Met Flyway (of Liquibase) in de applicatie draait de migratie bij het opstarten van de eerste nieuwe pod. Op dat moment serveren de oude pods nog verkeer, tegen het schema dat net is veranderd. Een migratie in deploy N moet dus werken met de code van deploy N−1. Een RENAME COLUMN doet dat niet, en een kolom die NOT NULL is zonder default ook niet: de oude code kent hem niet en laat hem bij een insert leeg. Expand–contract (Martin Fowler en Danilo Sato noemen het parallel change) knipt de wijziging op in stappen die elk compatibel zijn met de vorige.

Geverifieerd met Jackson 3.1.5 en Spring Boot 4.1.1 (Framework 7.0.9) op JDK 25: alle gedragingen in de tabel, met een kale JsonMapper én met de door Boot geconfigureerde mapper; de Jackson 2-vergelijking met 2.21.5. Het schemagedrag met H2 2.4.240, ook in MODE=PostgreSQL: een RENAME COLUMN laat SELECT psp_ref van de oude code falen (Column "PSP_REF" not found); ADD COLUMN … NOT NULL zonder default faalt op een gevulde tabel en slaagt op een lege, waarna een insert van de oude code faalt. Flyway, Liquibase en PostgreSQL zelf zijn niet gedraaid; wat hier over hen staat komt uit hun documentatie.

Uitgewerkt voorbeeld

De payment-service heeft drie contracten: de tabel payment, een publieke REST-API die merchants aanroepen (GET /payments/{id}), en het topic payment-captured, gelezen door de ledger-service en de payout-service van twee andere teams. De ledger matcht captures met het settlementrapport van de PSP op pspRef. Een collega wil de naam overal consistent maken. Een nette refactoring, in één PR:

Alle tests zijn groen: de testdatabase wordt vanaf nul gemigreerd, en de serialisatietest gebruikt dezelfde record aan beide kanten. Wat er in productie gebeurt, per contract:

  1. Database. De eerste nieuwe pod start, Flyway hernoemt de kolom, en de oude pods die nog verkeer serveren krijgen bij elke query op payment een SQL-fout. Paneel A uit het diagram. Na de rollout is het stil, maar een rollback naar de vorige versie kan niet meer zonder een handmatige terug-migratie.
  2. REST. Merchant-integraties lezen pspRef. Die is er niet meer. Een client met Jackson 3, of een andere tolerante reader, krijgt geen fout maar null, en zijn reconciliatie loopt stil vast. Een strikte client krijgt een exception. In beide gevallen is het incident bij hen, en jij ziet niets in je eigen logs.
  3. Event. De ledger draait de oude versie van PaymentCaptured. Het nieuwe veld pspReference wordt genegeerd, pspRef wordt null. Geen exception, geen DLT, geen alert: elke capture vanaf de deploy is ongematcht, en dat merkt Finance pas bij de dagafsluiting. Andersom gaat het ook mis: past de ledger zijn record wél aan en leest hij oude berichten opnieuw, dan is pspReference null.

Het punt: de rename is in Java gratis en op de lijn duur. Een reviewer vraagt bij elke naamwijziging in een record, entity of DTO: verandert hier alleen de Java-naam, of ook de naam die iemand anders ziet?

Oplossingen en hun prijs

A · Alleen de Java-naam wijzigen

De code wordt consistent, de contracten blijven gelijk. @Column(name = "psp_ref") op het veld en @JsonProperty("pspRef") op de recordcomponent. Geverifieerd: de record serialiseert weer als "pspRef" en leest oude berichten. Prijs: een naamverschil tussen code en lijn dat je met een annotatie documenteert. Geen coördinatie, geen migratie. Bijna altijd de juiste keuze voor een cosmetische rename.

public record PaymentCaptured(
        UUID eventId,
        UUID paymentId,
        @JsonProperty("pspRef") String pspReference,
        long amountMinor,
        String currency) {}

B · Expand–contract op het contract

Wil je de nieuwe naam echt op de lijn, dan stuur je een periode beide velden (expand), laat je consumers overstappen (migrate) en haal je het oude weg als niemand het meer leest (contract). Voor de tabel is dat het diagram. Prijs: weken doorlooptijd, en je moet weten wie je consumers zijn. Bij een topic betekent "niemand leest het meer" ook: er staan geen oude berichten meer in de retentie die nog verwerkt moeten worden.

C · Nieuwe versie of nieuw event-type

Voor een echte herstructurering (bijv. amountMinor + currency → amount-object): REST krijgt een v2 naast v1 (Spring Framework 7 API-versioning, hieronder), een event krijgt een nieuw type of topic (payment-captured.v2) dat een tijd naast het oude wordt gepubliceerd, via dezelfde outbox (module 3). Prijs: twee contracten onderhouden en testen, en een expliciete datum waarop het oude stopt.

Spring Framework 7 API-versioning: wat het wél en niet oplost

Nieuw in Framework 7: een versie als onderdeel van de mapping. Spring Boot 4 configureert hem met spring.mvc.apiversion.*.

PaymentController.java · application.properties
@GetMapping(path = "/payments/{id}", version = "1")PaymentV1 getV1(@PathVariable UUID id) { ... }       // pspRef, amountMinor@GetMapping(path = "/payments/{id}", version = "2+")PaymentV2 getV2(@PathVariable UUID id) { ... }       // pspReference, amount{value,currency}spring.mvc.apiversion.use.header=API-Versionspring.mvc.apiversion.default=1

Nagespeeld met MockMvc: zonder header krijg je v1 (de default), API-Version: 2 geeft v2, en 2.1, 3 of abc geven 400 (InvalidApiVersionException): standaard zijn alleen de versies die in controllers voorkomen ondersteund, en "2+" betekent "2 en elke latere ondersteunde versie". Een StandardApiVersionDeprecationHandler-bean (Boot pakt hem op) zet bij v1 de headers Deprecation (RFC 9745) en Sunset (RFC 8594), zodat clients zien dat er een einddatum is. Let op: zet je version in een mapping zonder dat er een strategie is geconfigureerd, dan start de context niet (API version specified, but no ApiVersionStrategy configured).

Wat het niet doet: het dekt alleen HTTP-requests. Je Kafka-events, je tabel en de JSON in een outbox-rij hebben er niets aan. En een tweede versie is code die je onderhoudt; het is het middel als een break onvermijdelijk is, niet de eerste reflex bij een rename (fix A is goedkoper).

Ook toevoegen kan breken

Toevoegen voelt veilig, en is dat meestal. Drie uitzonderingen die je in een review moet zien:

  • Een nieuwe enumwaarde. Een oude consumer met een eigen enum CaptureStatus { CAPTURED, FAILED } krijgt "PARTIALLY_CAPTURED" en gooit InvalidFormatException. Op Kafka gebeurt dat in de deserializer, vóór je listener; zonder ErrorHandlingDeserializer kan Spring het record niet eens aan de error handler geven. De verdediging hoort bij de lezer en moet er vóór de nieuwe waarde zijn: een UNKNOWN-waarde die bewust wordt afgehandeld. Let op: @JsonEnumDefaultValue alléén doet niets; de feature moet aan, globaal of per veld:
public enum CaptureStatus { CAPTURED, FAILED, @JsonEnumDefaultValue UNKNOWN }

// globaal, voor de Boot-mapper (REST):
spring.jackson.datatype.enum.read-unknown-enum-values-using-default-value=true

// per veld, werkt met elke mapper (ook die van je Kafka-deserializer):
record PaymentCaptured(...,
    @JsonFormat(with = JsonFormat.Feature.READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE)
    CaptureStatus status) {}

Daarna moet UNKNOWN ergens heen: in een exhaustive switch (module 6b) een eigen tak die het bericht parkeert en alarmeert, niet een default die het als CAPTURED behandelt.

  • Een nieuw primitief veld in een record. long feeMinor erbij, en de nieuwe consumer leest een oud bericht zonder dat veld: Jackson 3 gooit MismatchedInputException, omdat FAIL_ON_NULL_FOR_PRIMITIVES nu standaard aan staat. Onder Jackson 2 werd het stil 0, wat bij een fee net zo fout is. Gebruik Long en geef null een betekenis ("nog niet bekend").
  • Een NOT NULL-kolom zonder default. Op een gevulde tabel faalt de migratie; de pod start niet, de rollout stopt. Op een lege tabel (CI, een verse testomgeving) slaagt hij, dus je pipeline is groen. En als hij slaagt, faalt elke insert van de oude pods. Met een default (boolean not null default true) gaat het wel goed: bestaande rijen en inserts van oude code krijgen de default, en PostgreSQL slaat een niet-volatiele default sinds versie 11 op in de metadata, zonder de tabel te herschrijven. Heeft de kolom geen zinnige default, dan expand–contract: nullable toevoegen, vullen, en pas daarna NOT NULL.

Wanneer het géén probleem is

  • Een interne API met één consumer in dezelfde deploy. De backend en de frontend die in hetzelfde artefact worden uitgerold, een module die alleen door een andere module in dezelfde JVM wordt aangeroepen. Hernoem vrij, de compiler of je end-to-end-test vindt de rest. Eén voorbehoud: een single-page app die in de browser nog de oude bundel heeft, roept na de deploy een paar minuten de nieuwe API aan.
  • Voor de eerste release. Een feature achter een flag zonder productiedata en zonder consumers: er is nog niets om compatibel mee te zijn. Een migratie hernoemen of aanpassen kan nu nog, later niet meer (Flyway controleert checksums van toegepaste migraties).
  • Een deploy met downtime. Als de service bewust met een recreate-strategie of in een onderhoudsvenster uitrolt, draaien oud en nieuw nooit tegelijk tegen de database. De kolomrename is dan veilig voor de database, niet voor externe lezers.
  • Additieve wijzigingen met een betekenisvolle null. Een nieuw optioneel veld in een response of event, een nullable kolom: dat is precies de expand-stap. Daar hoeft geen versie of ceremonie omheen.

Zwaarte: blocker als consumers buiten je deploy stil verkeerde data krijgen (rename of weggehaald veld op een publieke API of een topic waar geld aan hangt), als een nieuwe enumwaarde consumers zonder UNKNOWN-afhandeling bereikt, of als een migratie de draaiende versie breekt (rename, drop) · major als het luid faalt en herstelbaar is (een migratie die op productiedata niet start), of als de consumers bekend zijn en het afgestemd kan worden maar dat nog niet is · minor of laat gaan bij één consumer in dezelfde deploy. De vraag die de zwaarte bepaalt: wie leest dit nog meer, en merkt die het?

Zegt niet wélk contract breekt, voor wie, of hoe het faalt. En het voorstel is het duurste dat er is, voor een probleem dat met een annotatie verdwijnt. Wordt beantwoord met "het is maar een rename".

issue (blocking) Deze rename verandert drie contracten tegelijk. Antwoordsleutel tonen

Regels 8 en 34 blocker Een nieuwe enumwaarde in een event dat twee andere teams lezen, elk met een eigen CaptureStatus zonder PARTIALLY_CAPTURED. Hun deserializer gooit InvalidFormatException vóór de listener; zonder ErrorHandlingDeserializer komt het record niet eens bij de error handler, en mét belandt het na de retries in een DLT of alleen in het log. In beide gevallen worden deelcaptures niet uitbetaald en niet geboekt, en de eerste deelcapture in productie is het moment waarop je het ontdekt. Voorstel: eerst bij ledger en payout een tolerante UNKNOWN laten uitrollen (met READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE en een expliciete afhandeling), pas daarna de nieuwe waarde publiceren. Alternatief: status blijft CAPTURED en het nieuwe veld finalCapture draagt de informatie; dat is additief.

Regel 2 major NOT NULL zonder default op een tabel met 40 miljoen rijen: in productie faalt V31, de eerste nieuwe pod start niet en de rollout blijft hangen. In CI en op een verse testomgeving is de tabel leeg en slaagt hij wel; vandaar groen. En zelfs als hij slaagt, falen de inserts van de oude pods, die sequence_no niet kennen. Major en geen blocker omdat het luid faalt zonder dataschade (PostgreSQL rolt de DDL terug), maar het blokkeert de release. Voorstel: nullable toevoegen; v.next vult hem; backfill (bestaande captures zijn allemaal volgnummer 1, dus default 1 kan hier ook, en is dan de simpelste fix); daarna eventueel set not null.

Regels 32–39 blocker Uit module 3. kafka.send binnen de transactie: rolt de commit terug, dan staat PaymentCaptured al op het topic en betaalt payout een capture uit die niet bestaat; faalt de send stil (de future wordt niet bekeken), dan wordt een capture nooit uitbetaald. Payout hangt er geld aan. Voorstel: in dezelfde transactie naar de outbox schrijven. Ook dan geldt: eventId hoort in de outbox-rij vast te liggen, niet bij elke publicatie een nieuwe UUID.

Regels 44–49 minor Uit module 5. De test heet backward compatible maar serialiseert en deserialiseert met dezelfde record; hij is groen bij elke wijziging, ook bij een rename. Hij test Jacksons roundtrip, niet het contract. Een test die wél iets zegt: een vastgelegd oud bericht (payment-captured-v3.json, zonder sequenceNo) lezen met de nieuwe record. Die test was hier rood geworden: int sequenceNo is primitief, en Jackson 3 gooit MismatchedInputException op het ontbrekende veld; relevant zodra deze service of een andere oude berichten opnieuw leest. Gebruik Integer, of een compact constructor met een default. De richting naar de consumers dek je met een consumer-driven contract test of een compatibiliteitscheck in de Schema Registry.

Maar @JsonProperty("pspRef") houdt de naam op de lijn gelijk; alleen de Java-naam verandert. Dit is fix A. Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 1 · voorspellen

    De ledger draait nog met de oude record en de standaard Jackson 3-instellingen. Er komt een bericht binnen van de nieuwe producer.

    Ledger · record

    record PaymentCaptured(
    UUID paymentId,
    String pspRef,
    long amountMinor) {}

    Bericht op het topic

    {"paymentId": "8f0c…",
 "pspReference": "PSP-81723",
 "amountMinor": 2500}

    Wat gebeurt er bij het deserialiseren?

    Antwoord tonen

    Niets zichtbaars: het bericht wordt gelezen met pspRef = null.

    Waarom

    • FAIL_ON_UNKNOWN_PROPERTIES staat in Jackson 3 standaard uit, dus pspReference wordt genegeerd.
    • pspRef ontbreekt; een ontbrekende referentiecomponent wordt null.
    • Met een kale Jackson 2-ObjectMapper was het een UnrecognizedPropertyException geweest. Luid is hier beter dan stil.

    Let op

    • De tolerant reader is niet de fout; het weghalen van pspRef aan de producerkant is dat. Een lezer kan zich wel beschermen door verplichte velden te valideren (bijv. in de compact constructor) en het bericht te parkeren in plaats van door te boeken.
  2. Vraag 2Doel 1 · voorspellen

    De payout-service voegt een veld toe aan zijn eigen record en zet een nieuwe consumer group op die het topic vanaf het begin leest (auto.offset.reset=earliest, zeven dagen retentie). De producer stuurt feeMinor pas sinds gisteren mee.

    record PaymentCaptured(UUID paymentId, String pspRef,
                       long amountMinor, long feeMinor) {}

    Wat gebeurt er met de berichten van vóór gisteren?

    Antwoord tonen

    Elk oud bericht faalt met MismatchedInputException: Cannot map `null` into type `long`.

    Waarom

    • Een ontbrekende recordcomponent krijgt null, en FAIL_ON_NULL_FOR_PRIMITIVES staat in Jackson 3 standaard aan.
    • Onder Jackson 2 werd het stil 0: een fee van nul. Ook fout, alleen niet zichtbaar.
    • Dit is een backward-probleem: nieuwe lezer, oude data. Het treft replays, nieuwe consumer groups en het opnieuw verwerken van een DLT.

    In de review

    issue: long feeMinor faalt op elk bericht van vóór de producer-deploy (Jackson 3, FAIL_ON_NULL_FOR_PRIMITIVES), en de nieuwe consumer group leest er zeven dagen van. Maak het Long en behandel null als "fee onbekend", of reken hem uit zoals voorheen.

  3. Vraag 3Doel 2 · uitschrijven

    Elke betaling moet een merchant_account_id krijgen, verplicht. Er is geen zinnige default; de waarde komt uit de merchant-tabel. De tabel payment is groot en wordt continu beschreven. Rolling deploy, Flyway bij het opstarten.

    -- V40__merchant_account.sql (voorstel in de PR)
alter table payment add column merchant_account_id uuid not null;

    Welke stappen, verdeeld over welke deploys, stel je voor?

    Antwoord tonen

    Drie deploys: nullable toevoegen en vullen bij schrijven; backfill; daarna pas NOT NULL.

    Stappen

    • Deploy 1: add column merchant_account_id uuid (nullable). De nieuwe code vult hem bij elke insert. Oude pods laten hem leeg, en dat mag nog.
    • Deploy 2: backfill in batches (update … where merchant_account_id is null, per paar duizend rijen), pas als er geen oude pods meer zijn, anders komen er na de backfill nog lege rijen bij.
    • Deploy 3: NOT NULL afdwingen. Op PostgreSQL scant set not null de hele tabel onder een exclusieve lock; je voorkomt dat met eerst add constraint … check (merchant_account_id is not null) not valid, dan validate constraint (zonder schrijfblokkade), en dan set not null, dat de scan overslaat omdat de check al bewijst dat er geen null is.

    Let op

    • De voorgestelde migratie faalt in productie (gevulde tabel) maar slaagt in CI (lege tabel). Een migratietest tegen een kopie of een geseede database met productieachtige data vangt dat.
  4. Vraag 4Doel 3 · kiezen en verdedigen

    Het team wil amountMinor + currency in de publieke API vervangen door een object amount: {value, currency}. Hetzelfde veld zit ook in het event PaymentCaptured. Voorstel in de PR: @GetMapping(version = "2+") met de nieuwe vorm, v1 blijft bestaan met een Sunset-datum, en het event wordt in dezelfde PR mee aangepast.

    Wat vind je van het voorstel, voor REST en voor het event apart?

    Antwoord tonen

    Voor REST passend; voor het event lost het niets op: daar is de wijziging nog steeds breaking.

    Waarom

    • Een typewijziging (long → object) is breaking in beide richtingen; geen tolerant reader die dat opvangt. Een versie naast de oude is dan het juiste middel.
    • Clients zonder header blijven v1 krijgen (met spring.mvc.apiversion.default=1), en de deprecation handler zet Deprecation/Sunset in de responses.
    • API-versioning zit in de HTTP-mapping. Het event gaat via Kafka en heeft er niets aan: een oude ledger krijgt een object waar hij een long verwacht, MismatchedInputException.

    In de review

    issue (blocking): v2 voor de REST-API is prima. Maar PaymentCaptured verandert in dezelfde PR van vorm, en ledger en payout krijgen dan een object waar ze long amountMinor lezen: elke capture faalt bij het deserialiseren. Voorstel: in het event het nieuwe object naast amountMinor/currency zetten (additief), of een payment-captured.v2-topic dat een tijd naast het oude wordt gevuld.

  5. Vraag 5Doel 4 · zwaarte en comment

    Twee PR's met dezelfde wijziging: in een response-record wordt pspRef hernoemd naar pspReference.

    A · back-office

    // GET /internal/payments/{id}
// alleen gebruikt door de back-office-UI
// die in dezelfde jar wordt uitgerold

    B · merchant-API

    // GET /payments/{id}
// publiek, ~300 merchant-integraties,
// gedocumenteerd in de OpenAPI-spec

    Welke zwaarte geef je aan elk?

    Antwoord tonen

    A: laat gaan, hooguit een vraag. B: blocker.

    Waarom

    • A: één consumer, dezelfde deploy; past de UI in dezelfde PR mee aan, dan is er geen moment waarop ze elkaar niet begrijpen. Hooguit: een browser met de oude bundel ziet een paar minuten undefined.
    • B: consumers die je niet kent en niet kunt laten meedeployen, en ze falen stil (een tolerante client krijgt null). De wijziging is hetzelfde, de zwaarte zit aan de ontvangende kant.

    In de review

    issue (blocking): pspRef verdwijnt uit de publieke response; merchants die hem lezen krijgen null of een parse-fout, en wij zien daar niets van. Houd de wire-naam met @JsonProperty("pspRef"). Bij A: question: wordt de UI in dezelfde PR aangepast? Dan prima.
