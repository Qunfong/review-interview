JPA en N+1

Een lazy relatie ziet eruit als een gewoon veld. In de test met drie betalingen is de pagina snel. In productie draait de uitbetalingsrapportage voor een grote merchant 8.000 queries en houdt hij al die tijd een databaseconnectie vast.

Tijd 40 minStack Java 25 · Spring Boot 4 (Hibernate 7)

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Payment.merchant is een LAZY @ManyToOne. Vuurt payment.getMerchant().getId() een query af?
  2. Je zet een @OneToMany op EAGER. Hoeveel queries draait findByCustomerId voor een klant met 50 orders?
  3. Waarom werkt dezelfde lazy relatie wel in je controller, maar gooit hij een LazyInitializationException in een @Scheduled-job?

Wat er onder de motorkap gebeurt

Een query als findByMerchantId laadt alleen de kolommen van payment. Hibernate kan de relaties op twee manieren invullen zonder ze te laden:

  • Collecties (@OneToMany, @ManyToMany) krijgen een eigen collectieklasse van Hibernate, bijvoorbeeld PersistentBag voor een List. Die is leeg tot je hem voor het eerst aanraakt: size(), stream(), iterator(). Op dat moment gaat er één select … from refund where payment_id = ? naar de database, voor die ene betaling.
  • Enkelvoudige relaties (@ManyToOne met LAZY) krijgen een proxy: een subklasse waarin alleen de id is ingevuld. getId() kost niets. Elke andere getter laadt de entity. Omdat de persistence context per id maar één instantie bijhoudt, wordt elke unieke merchant maar één keer opgehaald.

Raak je in een lus of een stream().map(...) per rij een lazy collectie aan, dan krijg je 1 query voor de lijst plus N queries voor de collecties: N+1. Er staat geen query in de code. Je ziet een getter, of zoals in het voorbeeld hieronder een domeinmethode als refundedTotal() die intern over de collectie loopt.

Lazy laden werkt alleen zolang de persistence context open is. In een Spring-service is dat de transactie. Buiten de transactie is de entity detached en geeft de eerste aanraking een LazyInitializationException. Behalve in een webrequest: Spring Boot zet spring.jpa.open-in-view standaard aan. Een interceptor opent dan aan het begin van het request een EntityManager en sluit hem pas als de response is geschreven. Lazy laden "werkt" dan ook in je controller en tijdens het serialiseren naar JSON. Boot logt daarom bij het opstarten een WARN: spring.jpa.open-in-view is enabled by default.

Geverifieerd: de aantallen in B zijn gemeten met Spring Boot 4.1.1 (Hibernate 7.4.5) en H2, via Statistics.getPrepareStatementCount(). Ook gemeten: getMerchant().getId() op een lazy proxy kost 0 queries; getMerchant().getName() voor 50 betalingen van één merchant kost er 1.

De dagelijkse uitbetalingsrapportage: per merchant alle gecapturede betalingen van een dag, met het bedrag dat nog wordt uitbetaald na refunds. refundedTotal() is een nette domeinmethode op Payment die over refunds loopt. Code en test zien er goed uit.

Stap voor stap, voor een merchant met 8.000 betalingen op een drukke dag:

  1. findCaptured doet één query en geeft 8.000 managed Payment-entities terug. Elke refunds is een niet-geladen PersistentBag.
  2. De map roept per betaling refundedTotal() aan. refunds.stream() initialiseert de bag: één select per betaling. Samen 8.001 statements.
  3. Bij 1 ms per round trip is dat 8 seconden alleen aan netwerk, en al die tijd houdt de transactie een connectie uit de pool vast. Draaien er tien van deze rapporten tegelijk, dan is de standaardpool van HikariCP (10 connecties) leeg.
  4. De integratietest met drie betalingen doet vier queries in een paar milliseconden en is groen. Niets in de test faalt op het aantal queries.

De rapportage klopt wel. N+1 is een performance- en beschikbaarheidsprobleem, geen correctheidsprobleem. Daarom komt het door de tests en pas in productie naar boven, bij de grootste klant.

Oplossingen en hun prijs

A · Fetch join in de query

select p from Payment p left join fetch p.refunds where …. Eén query; Hibernate 6 en 7 ontdubbelen de root-entities zelf (gemeten: 100 rijen, 50 payments), distinct is niet meer nodig. Gebruik left: een inner join fetch laat betalingen zonder refunds weg. Prijs: de query staat vast aan dit gebruik. Twee List-collecties tegelijk fetchen gooit een MultipleBagFetchException. Met paginering hangt het af van de Hibernate-versie (zie vraag 3).

B · @EntityGraph op de repositorymethode

@EntityGraph(attributePaths = "refunds") op een derived query. Zelfde SQL als A (gemeten: 1 statement), maar de query blijft een derived query en het fetchplan staat ernaast. Prijs: dezelfde grenzen als A, en het is minder zichtbaar: wie de methode hergebruikt, laadt altijd de refunds mee.

C · Batch fetching

spring.jpa.properties.hibernate.default_batch_fetch_size=16 (globaal) of @BatchSize(size = 16) op de relatie. De code verandert niet; Hibernate laadt de refunds van 16 betalingen tegelijk met where payment_id in (?, …). Gemeten: 5 statements in plaats van 51. Prijs: nog steeds ⌈N/16⌉ queries; bij 8.000 betalingen zijn dat er 501. Een uitstekend vangnet, geen oplossing voor een rapportage over grote aantallen.

D · DTO-projectie: laat de database rekenen

De rapportage heeft geen entities nodig, alleen getallen. Een constructor-expressie met sum en group by geeft één query, geen managed entities, geen dirty-checking-snapshots en geen refund-rijen in het geheugen. Prijs: de berekening staat nu in JPQL in plaats van in refundedTotal(); je hebt de regel op twee plekken. Voor een read-only rapport over veel rijen is dit meestal de beste keuze.

Niet: fetch = FetchType.EAGER op refunds. Dat "werkt" in de zin dat de LazyInitializationException verdwijnt, maar findCaptured doet daarna nog steeds 1 + N queries (gemeten: 51 voor 50), want een eager collectie wordt na een JPQL-query met losse selects geladen. Alleen findById/em.find gebruikt er een join voor. En je kunt EAGER per query niet meer uitzetten: elke plek die een Payment laadt, betaalt voortaan voor de refunds, ook de checkout die ze nooit leest.

Wanneer het géén probleem is

  • N is klein en begrensd door het domein, op een pad dat zelden draait. Een order met hooguit drie verzendadressen op een adminscherm dat tien keer per dag wordt geopend: vier queries van een milliseconde. Een fetch join maakt de code daar niet beter van.
  • N is begrensd door paginering en batch fetching staat globaal aan. Een pagina van 50 rijen met default_batch_fetch_size=50 kost twee queries per relatie. Kijk of de instelling er staat voordat je comment.
  • getId() op een lazy @ManyToOne laadt niets: de proxy kent de id al. p.getMerchant().getId() in een lus is gratis.
  • Een @ManyToOne met weinig unieke waarden. 8.000 betalingen van één merchant: getMerchant().getName() laadt die merchant één keer, daarna komt hij uit de persistence context. De "N" is het aantal unieke merchants, niet het aantal rijen.
  • Een lus die bewust per item een transactie doet, zoals een batchjob die per merchant een eigen uitbetaling verwerkt. Daar zijn N queries de bedoeling; de vraag is dan of elke iteratie zelf efficiënt laadt.

Zwaarte: blocker als N meegroeit met de data (geschiedenis van een merchant, alle orders van vandaag) op een request-pad of in een job met een deadline, of als in-memory paginering een hele tabel laadt · major als EAGER wordt toegevoegd, als een entity rechtstreeks als API-response wordt geserialiseerd, of als een begrensde N+1 op een hot path zit · minor bij een begrensde N (paginagrootte) op een rustig pad · laat gaan bij een kleine, domeinbegrensde N of als batch fetching het al afvangt.

Zo schrijf je het op

Zwak

N+1 hier. Gebruik een fetch join.

Waar dan? refundedTotal() ziet er niet uit als een query. Geen orde van grootte, dus de auteur denkt "drie extra queries, wat maakt het uit". En het voorstel is niet per se de beste fix voor een rapportage.

Sterk

issue (blocking) refundedTotal() loopt over de lazy refunds-collectie, dus in deze map gaat er per betaling een extra select naar de database. Voor merchant X met ~8.000 betalingen per dag zijn dat 8.001 queries in één transactie, en die houdt al die tijd een connectie vast.

Voorstel: deze rapportage heeft geen entities nodig. Een DTO-projectie met sum(r.amount) en group by doet het in één query. Als je de domeinmethode wilt houden: left join fetch p.refunds in findCaptured.

Vangnet: een test die met Statistics.getPrepareStatementCount() asserteert dat het aantal queries niet meegroeit met het aantal betalingen.

Antwoordsleutel tonen

Regel 55 (met 58–65) blocker Uit module 1. nightly() roept settle() via this aan: de proxy wordt overgeslagen en er is geen transactie. Gevolgen: (1) findBySettledFalse… draait zonder omringende transactie; de gedeelde EntityManager sluit zijn persistence context direct na de aanroep en de entities zijn detached. Dát gaf de LazyInitializationException op refundedTotal(), en de auteur heeft het symptoom bestreden met EAGER. (2) markSettled() op regel 65 wijzigt detached entities. Er is geen persistence context die ze flusht, dus settled blijft false in de database. (3) Elke payouts.save commit los. De volgende nacht worden dezelfde betalingen opnieuw uitbetaald: dubbele uitbetaling. Nagespeeld: na this.settle() staan alle 50 betalingen nog op settled = false, na een aanroep via de proxy 0. Voorstel: settle in een eigen bean (of een TransactionTemplate), en per merchant een eigen transactie zodat niet 200.000 rijen in één persistence context zitten. Een integratietest die nightly() aanroept en het aantal settled = false telt, vangt dit.

Regel 10 major EAGER als fix. Het lost de oorzaak niet op (die zit op regel 55) en maakt het op twee manieren erger. In de job doet findBySettledFalse… nu 1 + N queries, met N ≈ 200.000: een eager collectie wordt na een JPQL- of derived query met losse selects geladen, net als de lazy lus. En elke andere plek die een Payment laadt (checkout, webhooks, chargebacks) haalt voortaan ook de refunds op, zonder dat je dat per query nog kunt uitzetten. Voorstel: terug naar LAZY, de transactie repareren, en in de job de refunds meenemen met een fetch join, @EntityGraph of, beter, een DTO-projectie met sum per merchant.

Regels 23–27 major Fetch join op een collectie gecombineerd met Pageable. Op Hibernate 7.2 (Boot 4.0) kan dat niet in SQL: Hibernate logt HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory, haalt alle betalingen van de merchant met hun refunds op en knipt de pagina er in Java uit. Voor een grote merchant is dat per paginaweergave de hele geschiedenis in het geheugen: richting blocker. Pas sinds Hibernate 7.4 (Boot 4.1) gaat de limit in een subquery naar de database. Voorstel: pagineer op ids en haal daarna die 50 op met hun refunds, of laat de fetch join weg en gebruik @BatchSize. Zet hibernate.query.fail_on_pagination_over_collection_fetch=true, dan faalt dit al in de test.

Regel 41 minor getChargebacks() is lazy en niet meegefetcht: per rij een extra query, dus 50 per pagina. De N is begrensd door de paginagrootte, vandaar minor. Twee opmerkingen voor de comment. Dit werkt alleen dankzij open-in-view: de controller heeft geen transactie, de queries lopen in de view-sessie. Zet het team OSIV uit (wat aan te raden is), dan gooit deze regel een LazyInitializationException. En je kunt chargebacks niet simpelweg in dezelfde fetch join opnemen: twee List-collecties tegelijk geeft een MultipleBagFetchException. Voorstel: een exists-subquery in een DTO-projectie, of @BatchSize op chargebacks.

Regels 38 en 62 geen probleem De afleider. p.getMerchant().getId() op een lazy @ManyToOne: de proxy kent de id al, er gaat geen query af (gemeten: 0 extra statements). Een comment "N+1 op merchant" kost je hier geloofwaardigheid. Pas bij getMerchant().getName() zou Hibernate laden, en dan nog één keer per unieke merchant.

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 1 · herkennen en tellen

    findByCapturedAtAfter geeft 200 betalingen terug van in totaal 3 merchants. merchant en refunds zijn allebei LAZY. Alles draait in één transactie.

    payments.findByCapturedAtAfter(since).stream()
    .map(p -> new Row(
        p.getMerchant().getId(),
        p.getMerchant().getName(),
        p.getRefunds().size()))
    .toList();

    Hoeveel SQL-statements gaan er naar de database?

    Antwoord tonen

    204: 1 voor de lijst, 0 voor de ids, 3 voor de merchants, 200 voor de refunds.

    Waarom

    • getId() op een proxy laadt niets.
    • getName() laadt de merchant, maar de persistence context houdt per id één instantie bij. Drie unieke merchants zijn drie queries.
    • getRefunds().size() initialiseert elke collectie apart: 200 queries. Hier zit de echte N+1.

    In de review

    • Zet je comment op de regel met getRefunds(), niet op de merchant. Heb je alleen het aantal nodig, dan is count in een DTO-projectie beter dan een collectie laden om size() te vragen.
  2. Vraag 2Doel 2 · kiezen

    Een collega wil de N+1 op zowel refunds als chargebacks (beide List) in één keer oplossen:

    @Query("""
    select p from Payment p
    left join fetch p.refunds
    left join fetch p.chargebacks
    where p.merchant.id = :merchantId""")
List<Payment> findWithEverything(Long merchantId);

    Wat gebeurt er, en wat stel je voor?

    Antwoord tonen

    Hibernate weigert: MultipleBagFetchException: cannot simultaneously fetch multiple bags.

    Waarom

    • Een List zonder @OrderColumn is voor Hibernate een bag: duplicaten zijn toegestaan. Twee joins geven een cartesisch product (refunds × chargebacks per betaling), en Hibernate kan dan niet meer zien welke duplicaten echt zijn.
    • De collecties omzetten naar Set haalt de exception weg, maar niet het cartesisch product. Bij 10 refunds en 10 chargebacks komen er 100 rijen per betaling over de lijn.

    Beter

    • Fetch één collectie met een join, en laat de tweede via batch fetching laden (@BatchSize of default_batch_fetch_size). Of twee queries: eerst met refunds, dan dezelfde ids met chargebacks; de persistence context voegt ze samen.
    • Of, voor een leesscherm: een DTO-projectie die alleen de aantallen of totalen ophaalt.
  3. Vraag 3Doel 2 · versie-afhankelijk gedrag

    Dezelfde repositorymethode, in twee services: de ene op Spring Boot 4.0 (Hibernate 7.2), de andere op Boot 4.1 (Hibernate 7.4).

    @Query(value = "select p from Payment p left join fetch p.refunds where p.merchant.id = :id order by p.id",
       countQuery = "select count(p) from Payment p where p.merchant.id = :id")
Page<Payment> page(Long id, Pageable pageable);   // aangeroepen met PageRequest.of(1, 10)

    Wat doet de database in beide services?

    Antwoord tonen

    Op 7.2 geen limit in SQL: alles wordt opgehaald en in het geheugen gepagineerd. Op 7.4 gaan offset en fetch first in een subquery naar de database.

    Waarom

    • Een limit op een join met een collectie telt rijen, geen betalingen. Hibernate 6 en 7 vóór 7.4 lossen dat op door zonder limit te queryen en de pagina in Java te knippen. Daarbij loggen ze HHH90003004 … applying in memory; nagespeeld met Hibernate 6.4.
    • Hibernate 7.4 zet de paginering in een afgeleide tabel: from (select … from payment … offset ? rows fetch first ? rows only) left join refund …. Gemeten met Boot 4.1.1: 2 statements (pagina + count), 10 betalingen met elk hun refunds, geen waarschuwing.

    In de review

    • Kijk naar de Boot-versie van de service voordat je hierover commentaar geeft. Op oudere versies is het major tot blocker, afhankelijk van hoe groot de tabel is. Met hibernate.query.fail_on_pagination_over_collection_fetch=true wordt het een harde fout in plaats van een logregel.
  4. Vraag 4Doel 3 · uitleggen

    Het team zet spring.jpa.open-in-view=false om de opstartwaarschuwing weg te krijgen. Deze endpoint heeft geen @Transactional en draaide tot nu toe zonder problemen:

    @GetMapping("/merchants/{id}/payments")
List<View> list(@PathVariable Long id) {
    return payments.findByMerchantId(id).stream()
        .map(p -> new View(p.getId(), p.refundedTotal()))
        .toList();
}

    Wat gebeurt er nu, en wat was er eigenlijk al mis?

    Antwoord tonen

    De endpoint geeft een LazyInitializationException (no session). Hij deed al die tijd 1 + N queries.

    Waarom

    • Met OSIV aan houdt een interceptor de EntityManager open tot de response geschreven is. Lazy laden "werkte" dus, buiten elke service-transactie. Gemeten: 200 OK en 51 statements voor 50 betalingen.
    • Met OSIV uit sluit de persistence context zodra de repository-aanroep klaar is. De entities zijn detached; de eerste refunds.stream() faalt.

    In de review

    • OSIV uitzetten is de goede richting, maar het maakt verborgen lazy loading zichtbaar. Zoek vooraf naar controllers zonder transactie die entities aanraken of teruggeven, en geef die een service-methode met een DTO-projectie of fetch join. Een entity als JSON-response is extra riskant: de serializer loopt alle getters langs, ook de lazy relaties.
