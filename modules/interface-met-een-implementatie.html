Module 6a · D3 Ontwerpprincipes

Interface met één implementatie

Wie elk XService/XServiceImpl-paar afschiet, verspeelt krediet. Wie ze allemaal doorlaat, mist de ene interface die het SDK van de betaalprovider uit het domein had moeten houden. En wie op jouw advies de interface weghaalt en de class final maakt, krijgt een context die niet start, of erger: een NullPointerException pas bij de eerste echte aanroep.

Tijd 40 minStack Java 25 · Spring Boot 4 (Framework 7)Bouwt op module 1 (proxies)

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Welk soort proxy maakt Spring Boot standaard voor een @Transactional-bean die een interface implementeert: een JDK dynamic proxy of een CGLIB-subclass?
  2. Kan Mockito 5 een concrete final class mocken zonder extra configuratie?
  3. PaymentGateway heeft één implementatie, AdyenPaymentGateway. Hoort de interface in het pakket van de service die hem aanroept, of naast de implementatie? Waarom maakt dat uit?

Wat er onder de motorkap gebeurt

Een interface kost iets: elke signatuurwijziging raakt twee bestanden, "Go to declaration" landt op de interface in plaats van op de code, en de lezer moet uitzoeken welke implementatie actief is. Wat hij oplevert hangt niet af van het aantal implementaties, maar van wie hem bezit en welke kant de afhankelijkheid op wijst.

Drie historische redenen, en wat er van over is

Proxies voor @Transactional, @Async, @Cacheable: vervallen

JDK dynamic proxies kunnen alleen interfaces implementeren; in oude Spring-configuraties kreeg een bean zonder interface daarom geen proxy. Spring Boot zet spring.aop.proxy-target-class standaard op true: Spring maakt een CGLIB-subclass van je bean, óók als die een interface implementeert. Een bean zonder interfaces krijgt sowieso een CGLIB-proxy.

Mocken in tests: vervallen

Mockito 5 gebruikt standaard de inline mock maker en mockt concrete en zelfs final classes. @MockitoBean (in Boot 4 de vervanger van het verwijderde @MockBean) werkt op een class net zo goed als op een interface.

Afhankelijkheidsrichting (dependency inversion): volledig geldig

De gebruiker (het domein) definieert wat hij nodig heeft, in zijn eigen taal; een adapter aan de rand implementeert dat. Dit is de enige reden die van de structuur van je code afhangt in plaats van van tooling, en hij werkt alleen als de interface aan de kant van de gebruiker staat.

Een interface die naast zijn enige implementatie staat, met dezelfde methodes en dezelfde eigenaar, keert geen afhankelijkheid om. Dat is een header-interface: een C-headerbestand in Java-vorm. Een interface die de gebruiker bezit, in zijn eigen pakket en met zijn eigen typen, is een port. Die heeft vaak precies één implementatie, en terecht.

Wat de proxy doet als de interface verdwijnt

Zonder interface (en met de Boot-default ook mét) maakt Spring een runtime-subclass van je bean die de geadviseerde methodes overschrijft en de transactie-interceptor ervoor zet. Die proxy-instantie wordt aangemaakt zonder je constructor te draaien, dus de velden van de proxy zelf zijn null; hij delegeert naar het echte object. Dat is precies wat misgaat bij "interface weg, en dan netjes final erop":

  • final class: CGLIB kan geen subclass maken. De context start niet: BeanCreationException … Could not generate CGLIB subclass of class …: Common causes of this problem include using a final class or a non-visible class. Luid, maar wel een kapotte build.
  • final methode: de subclass kan die methode niet overschrijven. De context start gewoon; Spring logt alleen een WARN: Public final method […] cannot get proxied via CGLIB. De aanroep draait op de proxy-instantie zelf, waar de repository null is: NullPointerException bij de eerste echte aanroep, en er is nooit een transactie gestart. Dit is dezelfde val als in module 1, nu veroorzaakt door een ontwerpcomment.

Performance is geen argument, in geen van beide richtingen: een interface-aanroep met maar één geladen implementatie kan de JIT devirtualiseren en inlinen.

Geverifieerd: de proxyclaims in deze module zijn nagespeeld met Spring Boot 4.1.1 (Framework 7.0.9, Mockito 5.23) op JDK 25: CGLIB-proxy ook mét interface, BeanCreationException bij een final class, WARN plus NPE zonder transactie bij een final methode, en mock() van een final class zonder configuratie.

De echte bug ontstaat in de volgende commit, als de auteur jouw comment opvolgt en het "goed" wil doen. Hij kent Effective Java (item 19: ontwerp en documenteer voor overerving, of verbied het) en maakt de class final:

Stap voor stap:

  1. Bij het opstarten ziet Spring een @Transactional-methode en wil een CGLIB-subclass maken.
  2. De class is final: BeanCreationException, de applicatie start niet. Vervelend, maar je ziet het in de PR-build.
  3. Gevaarlijker is de halve variant: alleen de methode final (public final Invoice issue(…)). Alles start, met één WARN in de log. Bij het eerste factuurverzoek draait issue op de proxy-instantie: NPE op orders, zonder transactie.
  4. Een @WebMvcTest met @MockitoBean InvoiceService en een unit-test met new InvoiceService(…) zijn allebei groen. Alleen een test die de echte bean uit de context aanroept, vangt het.

Oplossingen en hun prijs

A · Interface weg, class niet final

Hernoem InvoiceServiceImpl naar InvoiceService. Niet final, want hij wordt geproxied. Prijs: geen, zolang alles in één deploybare eenheid zit. Komt er ooit een echte tweede implementatie, dan is Extract Interface een refactoring van een minuut. Standaardkeuze voor nieuwe code.

B · Interface naar de gebruiker

Alleen als er echt een grens is: zet de interface in het pakket of de module van de aanroeper, in diens taal, en maak de implementatie package-private of intern. Prijs: een extra bestand en indirectie. Alleen de moeite waard als die grens bewaakt wordt (Spring Modulith, ArchUnit) of een extern systeem afschermt.

C · Laten staan

Gebruikt de hele codebase Interface + Impl, dan is één afwijkende service duurder dan honderd consistente. Prijs: de ceremonie blijft. Zet het op de teamagenda in plaats van het in deze PR uit te vechten.

Wanneer het géén probleem is

"Eén implementatie" is de verkeerde maat. Vraag: wat zou er moeten veranderen als deze interface er niet was? Is het antwoord "niets", dan is het ceremonie. In deze gevallen is het antwoord iets anders:

  • Port naar een extern systeem (betaalprovider, vervoerder, e-mail). De interface houdt SDK-typen en -exceptions buiten het domein, ook als er nooit een tweede provider komt. Het argument is niet "we gaan wisselen" maar "SDK-wijzigingen blijven aan de rand". Daarom is dit geen YAGNI: de interface lost een probleem van vandaag op. Voorwaarde: de signatuur bevat domeintypen (Money, PspReference), geen SDK-klassen.
  • Publieke API van een module. In Spring Modulith is het basispakket van een module de API en zijn subpakketten intern. Een interface in de API met een implementatie in …internal is een bewaakte grens.
  • Library of SPI. Code voor gebruikers die jij niet kent (ServiceLoader, een gedeelde starter). Zij kunnen geen Extract Interface doen; daar is de interface het contract.
  • Test-seam voor iets niet-deterministisch: tijd, ID-generatie, een externe dienst. Een in-memory fake in je tests is een tweede implementatie. java.time.Clock is het schoolvoorbeeld (een abstracte class: het gaat om de seam, niet om het keyword).
  • Door het framework geïmplementeerd. Spring Data-repositories en @HttpExchange-clients hebben nul handgeschreven implementaties. Geen discussie.
  • Bewust gekozen JDK-proxies (spring.aop.proxy-target-class=false). Zeldzaam, maar dan zijn de interfaces wél functioneel. Vraag het voordat je weghalen voorstelt.

Omgekeerd is het grotere probleem vaak een ontbrekende port: een domeinservice die direct een SDK-client injecteert en SDK-typen teruggeeft, of een "port" waarvan de signatuur JPA-entities of HTTP-typen (ResponseEntity) lekt. Dat zie je in een diff aan imports als com.adyen… of org.springframework.http… in een pakket dat domain of payment heet.

Zwaarte: blocker nooit voor de interface zelf, wel voor de bijwerking van het weghalen: final op een geproxiede class of methode · major als een interface een grens claimt maar vendortypen doorlaat op een plek waar de leverancier of zijn SDK echt verandert, of als een extern systeem zonder port tot in de API-respons lekt · minor / nit een header-interface in nieuwe code, in een team zonder conventie; schrijf het als suggestion (non-blocking) · laat gaan als het de bestaande conventie is, of een van de gevallen hierboven.

Zo schrijf je het op

Zwak

Waarom een interface als er maar één implementatie is? YAGNI. Graag weghalen.

Een principe zonder gevolg. De auteur kan terugroepen "maar dat is clean architecture", en dan heb je een smaakdiscussie. Het voorstel kan bovendien leiden tot de final-bug.

Sterk

suggestion (non-blocking) InvoiceService heeft één implementatie in hetzelfde pakket en één aanroeper, dus hij schermt niets af. De twee redenen uit de beschrijving gelden in Boot 4 niet meer: @Transactional werkt via een CGLIB-subclass op de class zelf, en @MockitoBean mockt de class direct. Nu kost hij bij elke signatuurwijziging twee bestanden.

Voorstel: interface weg, InvoiceServiceImpl → InvoiceService. Let op: niet final maken, anders kan Spring hem niet proxyen.

Of is dit bedoeld als API voor een andere module? Dan liever de interface daar neerzetten en de implementatie intern maken.

Wat de sterke versie doet: hij weerlegt de genoemde redenen in plaats van een principe te roepen, noemt de prijs, waarschuwt voor de valkuil die het voorstel zelf introduceert, en laat ruimte voor context die jij niet hebt.

Antwoordsleutel tonen

Regel 49 blocker final op een @Transactional-methode (deze module en module 1). CGLIB kan start niet overschrijven; de context start wel, met alleen een WARN in de log. De controller roept start aan op de proxy-instantie, waar carts null is: NPE op regel 50 bij elke checkout, en nooit een transactie. Comment: "issue (blocking): final weghalen; Spring proxyt deze bean via een subclass en kan een final methode niet onderscheppen. Een @SpringBootTest die start aanroept had dit gevangen."

Regels 48 + 51/58 major Uit module 1. Zodra final weg is, draait de HTTP-call naar DHL binnen een databasetransactie. De JDBC-connectie blijft vast zolang DHL antwoordt; bij een trage DHL loopt de connection pool leeg en lopen ook ongerelateerde endpoints vast. Voorstel: verzendkosten berekenen vóór de transactie (in de aanroeper, of een methode zonder @Transactional die daarna een transactionele bean aanroept), en alleen het opslaan transactioneel maken. Zet ook een timeout op de DhlRestClient.

Regels 60–61 major Uit de basis (foutpad). Elke exception wordt gratis verzending. Bij een DHL-storing, een time-out of een bug in de mapping op regel 59 verzendt de shop stil gratis, zonder log of metric. Voorstel: alleen de verwachte clientfout vangen en expliciet kiezen: checkout laten falen, of een vast fallbacktarief, met logging en een metric. Dat is een productbeslissing; vraag het.

Regels 4–8 (met 15 en 59) minor Deze module. De interface claimt een grens ("andere vervoerders"), maar de signatuur geeft DhlRateResponse terug, staat naast zijn implementatie, en CheckoutService leest op regel 59 DHL-velden uit. Een tweede vervoerder betekent tóch de interface en alle aanroepers wijzigen: hij beschermt niets. Kies: óf een echte port in checkout, in domeintaal (Money quote(Address, Weight), DHL-mapping in de adapter), óf de interface weglaten. Niet het aantal implementaties is het probleem, maar de lekkende signatuur. Staat multi-carrier echt op de roadmap, dan eerder major.

Regels 38, 52, 66–73 geen probleem De afleider. Clock als bean met één productie-implementatie is een test-seam: tests geven Clock.fixed(…) mee en kunnen "checkout verloopt na 30 minuten" deterministisch testen. Een comment "één implementatie, waarom een abstractie?" zou hier precies de verkeerde zijn. Package-private @Configuration is ook prima.

Regel 14 geen probleem @Component in plaats van @Service maakt functioneel niets uit. Hooguit een nit als het team daar een conventie voor heeft.

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 1 · herkennen

    Een interface met één implementatie in hetzelfde pakket. Zes andere modules gebruiken hem.

    package com.shop.notification;

public interface NotificationSender {
    void send(CustomerId to, Notification message);
}

class EmailNotificationSender implements NotificationSender { … }

    Ceremonie of grens, en wat check je om dat te beslissen?

    Antwoord tonen

    Hier een grens: de API van de notification-module. Zie je andere signalen, dan kan het alsnog ceremonie zijn.

    Wat je checkt

    • Eigenaar en zichtbaarheid: de implementatie is package-private, dus de zes modules kúnnen alleen via de interface. Is hij public en injecteert iemand hem direct, dan schermt de interface niets af.
    • Signatuur: alleen eigen typen (CustomerId, Notification), geen MimeMessage of SMTP-exceptions.
    • Pakket: dat interface en implementatie in hetzelfde pakket staan is hier geen bezwaar: het pakket ís de module, en de gebruikers zitten erbuiten.

    Let op

    • Vergelijk met InvoiceService uit het voorbeeld: daar zat de enige gebruiker in hetzelfde pakket, dus er was niets om af te schermen.
  2. Vraag 2Doel 2 · uitleggen

    payment/RefundService injecteert direct de SDK-client van de betaalprovider en geeft het SDK-responsobject terug aan de controller. Op je voorstel voor een port antwoordt de auteur: "YAGNI, we zitten contractueel vijf jaar vast aan deze provider."

    Klopt die redenering?

    Antwoord tonen

    Nee. De port is er niet om te kunnen wisselen, maar om de SDK aan de rand te houden; dat probleem bestaat vandaag al.

    Waarom

    • SDK-typen lekken nu via domein en controller tot in de API-respons. Een SDK-upgrade met gewijzigde modellen raakt controller, service en tests.
    • SDK-exceptions bepalen je foutafhandeling en (via het exceptiontype) je rollbackgedrag.
    • YAGNI gaat over speculatieve behoeften. "SDK-wijzigingen blijven in één klasse" is geen speculatie.

    In de review

    issue: de SDK-respons komt tot in onze API. Bij elke SDK-upgrade wijzigen controller, service en tests mee. Voorstel: een PaymentGateway-port in payment met onze eigen typen, implementatie in payment.adyen. Eén implementatie, en dat is prima: het gaat om waar de SDK mag komen, niet om wisselen.

  3. Vraag 3Doel 3 · voorspellen

    Een team heeft bewust JDK-proxies aangezet. InvoiceServiceImpl implements InvoiceService heeft een @Transactional-methode. Een nieuwe klasse injecteert de concrete class:

    # application.properties
spring.aop.proxy-target-class=false

public ReminderJob(InvoiceServiceImpl invoices) { … }

    Wat gebeurt er bij het opstarten, en wat als je in dit team de interface weghaalt?

    Antwoord tonen

    Met de interface start de context niet; zonder interface start hij wel.

    Waarom

    • Met de interface krijgt de bean een JDK dynamic proxy die alleen InvoiceService implementeert, geen InvoiceServiceImpl is. Injectie faalt: BeanNotOfRequiredTypeException, "expected to be of type InvoiceServiceImpl but was actually of type jdk.proxy2.$Proxy…".
    • Zonder interfaces valt Spring automatisch terug op een CGLIB-subclass, en dan werkt het.

    Les

    • Kijk naar de proxyconfiguratie voordat je over interfaces discussieert. In dit team zijn de interfaces functioneel, en is de fix: injecteer de interface.
  4. Vraag 4Doel 3 · voorspellen

    Na je comment haalt de auteur de interface weg en maakt alleen de methode final. Beide tests zijn groen:

    A · controllertest

    @WebMvcTest(InvoiceController.class)
class InvoiceControllerTest {
    @MockitoBean InvoiceService invoices;
    …
}

    B · unit-test

    var service = new InvoiceService(
        ordersMock, invoicesMock, clock);
assertThat(service.issue(id))…

    Waarom vangen deze tests de fout niet, en welke test wel?

    Antwoord tonen

    Beide omzeilen de Spring-proxy; alleen een test die de echte bean uit de context aanroept, faalt.

    Waarom

    • A gebruikt een mock: de echte issue draait nooit.
    • B maakt het object met new: de velden zijn gevuld en er is geen proxy.
    • De fout zit alleen in de combinatie echte bean + CGLIB-proxy + final methode: daar draait de aanroep op de proxy-instantie met null-velden.

    Welke test wel

    • Een @SpringBootTest (of een slice die de service importeert) die de geïnjecteerde InvoiceService aanroept: NPE, direct. En de WARN bij het opstarten was al een signaal.
  5. Vraag 5Doel 4 · zwaarte en comment

    De codebase heeft ruim 150 XService/XServiceImpl-paren. Een junior opent een PR met nog twee, netjes volgens dat patroon, zonder final en zonder lekkende typen.

    Welke zwaarte geef je, en wat schrijf je?

    Antwoord tonen

    Laat gaan in de PR; breng het daarbuiten in bij het team.

    Waarom deze zwaarte

    • De junior volgt de conventie. Eén afwijkende service maakt de codebase minder voorspelbaar en zet de discussie op de verkeerde plek.
    • Er is geen gevolg voor correctheid; de kosten zijn ceremonie, verspreid over 150 plekken. Dat is een teambesluit (ADR of tech-overleg), geen PR-bevinding.

    In de review

    thought (non-blocking): prima volgens onze huidige conventie. Ik ga voorstellen om voor nieuwe services zonder modulegrens de interface weg te laten (CGLIB-proxies en Mockito maken hem niet meer nodig). Niets aan doen in deze PR.
