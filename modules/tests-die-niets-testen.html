Module 5 · D4 Testen

Tests die niets testen

De refund-service heeft een test, de build is groen en de coverage-tool kleurt de methode helemaal groen. Toch kan een merchant op een betaling van €100 twee keer €80 terugboeken. De test controleerde dat er werd gebeld en opgeslagen, maar niet met welk bedrag.

Tijd 40 minStack Java 25 · Spring Boot 4 (JUnit 6, Mockito 5, AssertJ)

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Je test voert elke regel van een methode uit. Noem een bug die er toch doorheen komt.
  2. Wat moet er in de code veranderen om verify(refunds).save(any()) rood te krijgen? En welke fouten laat deze regel door?
  3. Wat geeft een Mockito-mock terug voor een niet-gestubde methode met returntype long? En voor Optional<Payment>?

Wat er onder de motorkap gebeurt

Een test vangt een bug alleen als drie dingen tegelijk waar zijn:

  1. Bereikt: de test voert de foute code uit. Dit is het enige wat coverage meet.
  2. Zichtbaar: met de input van déze test geeft de foute code een andere uitkomst dan de goede code. Een refund van 80 op een betaling van 100 waarop nog niets is terugbetaald, geeft hetzelfde resultaat of je nu tegen het restbedrag controleert of tegen het oorspronkelijke bedrag. Het verschil zit bij de tweede refund, en die input zit niet in de test.
  3. Gecontroleerd: een assert vergelijkt die uitkomst met een specifieke verwachte waarde. isNotNull() en verify(psp).refund(any(), anyLong(), any()) slagen voor elk bedrag.

Mocks spelen bij stap 2 en 3 een eigen rol. Een stub (when(...).thenReturn(...)) is input die je zelf bepaalt. Wat je niet stubt, krijgt een standaardwaarde: 0 voor een long, Optional.empty() voor een Optional, een lege lijst voor een List. Als de logica in de gemockte methode zit, bijvoorbeeld een sum-query, test je die logica niet. Je test dan het getal dat je zelf hebt ingevuld, of de standaardwaarde 0. Een verify is een assert op een interactie: hij faalt als een aanroep verandert, niet als een waarde fout is. Daardoor is een test die vooral uit verify(...) bestaat tegelijk te zwak (een fout bedrag komt erdoor) en te breekbaar (een correcte refactoring die een andere repositorymethode aanroept, maakt hem rood).

Mutation testing automatiseert stap 2 en 3. PIT (pitest) past de bytecode steeds op één plek aan: > wordt >=, - wordt +, een return wordt null, een void-aanroep verdwijnt. Daarna draait PIT alleen de tests die die regel raken. Faalt er een test, dan is de mutant gedood. Blijft alles groen, dan overleeft hij: op die plek kan het gedrag veranderen zonder dat een test het merkt. De mutation score is het percentage gedode mutanten. Anders dan line coverage meet die score ook of de asserts iets controleren.

Geverifieerd: PIT stond niet lokaal. De mutanten zijn daarom met de hand toegepast, met dezelfde operatoren als PIT's standaardset (Conditionals Boundary, Negate Conditionals, Math, Null Returns). Daarna draaiden beide testklassen per mutant (Spring Boot 4.1.1-parent, JUnit Jupiter 6.0.3, Mockito 5.23.0, JDK 25). Let op: PIT's Math-mutator werkt op operatoren als - en +, niet op BigDecimal.subtract(). Een methode-aanroep vervangen valt onder een optionele mutator. Daarom rekent het voorbeeld in minor units (long-centen), zoals veel betaalsystemen doen.

Uitgewerkt voorbeeld

Een PR met de titel "Refunds: controle op restbedrag". Bedragen staan in centen. De auteur heeft er een test bij geschreven, en die is groen.

Stap voor stap:

  1. De service controleert tegen payment.amountMinor() en niet tegen het restbedrag. Een eerste refund van €80 op €100 mag. Een tweede refund van €80 mag ook, want 8.000 is niet groter dan 10.000. De merchant boekt €160 terug op een betaling van €100, en de PSP voert beide uit.
  2. De test doet één refund op een betaling zonder eerdere refunds. Met die input gedragen de foute en de goede versie zich gelijk. Ook in een gecorrigeerde versie die refunds.sumRefunded(id) aanroept, blijft deze test groen: die methode is niet gestubd en de mock geeft 0 terug. De mock maakt bug en fix voor deze test identiek.
  3. Alle asserts slagen voor elk bedrag: isNotNull(), en drie keer verify met any(). Gemeten: de test blijft groen op de PR-versie. Ook R2 overleeft, een variant die de PSP het hele betaalbedrag laat terugboeken in plaats van de gevraagde €80.
  4. Instant.now() staat zowel in de service als in de test. Een test op de grens van het venster ("precies 180 dagen na capture mag nog") kun je zo niet betrouwbaar schrijven. Gemeten op deze Windows-machine: van 100.000 runs faalden er 133, omdat de klok tussen de twee now()-aanroepen net een tik verder ging. Dat is een flaky test die maar eens in de zoveel builds faalt.

Coverage helpt hier niet: de test loopt de hele happy path door en elke regel met een if wordt uitgevoerd. Coverage meet stap 1 uit het mechanisme, en het probleem zit in stap 2 en 3.

Oplossingen en hun prijs

A · Asserts op de uitkomst, inputs op de grens

Houd de mocks, maar stub wat de logica nodig heeft (sumRefunded = 8.000) en test aan beide kanten van de grens: precies de rest mag, één cent meer niet. Controleer het teruggegeven object op waarden en de PSP-aanroep op exacte argumenten. Gemeten: doodt alle negen mutanten. Prijs: de test kent nog steeds de repository-API. Met Mockito's strict stubs (standaard in MockitoExtension) faalt hij met UnnecessaryStubbingException zodra een refactoring sumRefunded niet meer aanroept.

B · Fakes in plaats van mocks voor je eigen opslag

Een in-memory RefundRepository (een Map plus een som) in plaats van stubs. De test zet toestand neer ("er is al €80 terugbetaald") en controleert toestand achteraf ("er staan nu twee refunds van samen €100"). Zo'n test overleeft een refactoring van de aanroepen. Prijs: de fake moet je onderhouden, en de echte query test hij niet. Een fout in de JPQL van sumRefunded blijft onzichtbaar (zie vraag 3).

C · De query tegen een echte database

Zit de logica in een query, dan hoort de test bij de query: @DataJpaTest voor de repository, bij voorkeur op dezelfde database als productie via Testcontainers en @ServiceConnection. Prijs: seconden per testklasse en Docker in CI. H2 is sneller, maar test een ander SQL-dialect: native queries, locking en jsonb gedragen zich daar anders.

D · Mutation testing als meetlat in CI

PIT met targetClasses op het domeinpakket, of scmMutationCoverage voor alleen de gewijzigde code, met withHistory voor snelheid en eventueel een mutationThreshold. Voor JUnit Jupiter heb je de pitest-junit5-plugin nodig. Controleer bij Boot 4 (JUnit 6) dat PIT je tests echt vindt: "0 tests" betekent dat de plugin niet werkt, niet dat alles gedood is. Prijs: looptijd, en er zijn altijd mutanten die je niet hoeft te doden (zie hieronder).

Twee details. Clock komt als bean binnen (@Bean Clock clock() { return Clock.systemUTC(); }) en in de test als Clock.fixed(...) via de constructor. Laat @InjectMocks hier weg: Mockito vult een constructorparameter waarvoor het geen mock heeft gewoon met null (gemeten), en dan krijg je een NullPointerException in plaats van een duidelijke fout. En de testnamen beschrijven nu de regel (rejects one cent above remaining), niet de methode (refund). Faalt er een, dan weet je welke regel er brak.

Dit voorbeeld laat twee onderwerpen bewust liggen. Twee gelijktijdige refunds kunnen allebei dezelfde sumRefunded lezen; dat is een concurrency-vraag (lock of constraint). En een PSP-aanroep binnen een transactie houdt een connectie vast (module 1).

Wanneer het géén probleem is

  • verify op een uitgaande opdracht aan de systeemgrens. "Er gaat geen geld naar de PSP als de refund wordt geweigerd" kun je nergens anders aan zien dan aan de aanroep. Daar is then(psp).shouldHaveNoInteractions() of then(psp).should().refund("psp-1", 2_000, "EUR") precies de goede assert. Het verschil met de zwakke test: exacte argumenten en een extern systeem, geen any() op je eigen repository.
  • Een mock of WireMock voor de externe betaalprovider, ook in een @SpringBootTest (@MockitoBean PspClient; @MockBean bestaat in Boot 4 niet meer). Je wilt in CI geen echte refunds doen, en het contract met de PSP test je apart.
  • isNotNull() als opstap voor verdere asserts, of in een smoketest die alleen controleert of de context start. Het is pas een probleem als het de enige assert op logica is.
  • Mutanten die je laat leven: equivalente mutanten (de wijziging verandert het gedrag niet, bijvoorbeeld < → <= op een lusgrens die nooit gelijk kan zijn), logregels, gegenereerde toString/equals. Een mutation score van 100% is geen doel. De vraag is of de overlevenden op regels zitten die geld, toegang of data bepalen.
  • H2 in plaats van Testcontainers voor eenvoudige JPQL-CRUD in een team zonder Docker in CI. Pas bij native SQL, locking, on conflict of database-specifieke typen wordt het verschil een risico.
  • Instant.now() voor een audit-tijdstempel waar geen beslissing en geen test van afhangt. Hooguit een nit: het team kan beter overal Clock gebruiken.

Zwaarte: blocker als de test de enige bewaker is van een regel die geld verplaatst of toegang geeft, en je een concrete overlevende bug kunt noemen · major bij een test op bedrijfslogica die alleen uit verify(any()) en isNotNull() bestaat, bij een deadline of venster dat op now() leunt, bij Thread.sleep in CI, en bij een gemockte repository waar de query de logica is · minor bij een testnaam die het gedrag niet beschrijft, of een extra verify naast goede asserts · laat gaan bij mocks aan de systeemgrens en overlevende mutanten op logging of gegenereerde code.

Zo schrijf je het op

Zwak

Deze test is niet zo sterk, te veel mocks. Kun je er nog wat asserts bij zetten?

Welke asserts? De auteur voegt assertThat(result.amountMinor()).isEqualTo(8_000) toe, en de bug op de restcontrole blijft staan. "Te veel mocks" is een smaakdiscussie zolang je niet laat zien wat erdoor glipt.

Sterk

issue (blocking) Regel 14 controleert tegen het oorspronkelijke bedrag, niet tegen de rest. Twee refunds van €80 op €100 gaan allebei door. De test vangt dit niet: hij doet één refund zonder eerdere refunds, en de asserts (isNotNull, verify(any())) slagen voor elk bedrag. Ik heb het nagespeeld: de test blijft groen met de bug, en ook als de PSP het hele betaalbedrag krijgt.

Voorstel: remaining = amount - sumRefunded, en twee tests op de grens: precies de rest mag, rest + 1 cent geeft RefundExceedsRemaining én shouldHaveNoInteractions() op de PSP. Injecteer een Clock, dan kun je ook de 180-dagengrens exact testen.

Antwoordsleutel tonen

Regel 16, met 42–46 blocker De chargeback krijgt payment.amountMinor() als bedrag, niet n.amountMinor(). De notificatie-parameter 4_500 wordt nergens gebruikt. Een gedeeltelijke chargeback van €45 op een betaling van €100 wordt als €100 geboekt, en via het event op regel 17 haalt de ledger €100 van het saldo van de merchant. Tweede gevolg: autoAcceptIfSmall kijkt naar hetzelfde bedrag, dus een chargeback van €5 op een grote betaling wordt nooit automatisch geaccepteerd. De test open() geeft 4_500 mee, maar controleert het bedrag niet: isNotNull() en verify(chargebacks).save(any()) slagen voor elke waarde. Dit is de kern van deze module. Comment: noem de bug én de reden dat de test hem niet vangt, en stel een assert voor op cb.amountMinor() (4_500) en op het bedrag in het event.

Regels 16 en 45 major LocalDate.now(), terwijl er een Clock is geïnjecteerd (regel 9) die nergens wordt gebruikt. Drie problemen. (1) De test herhaalt de formule (LocalDate.now().plusDays(7)): als de regel "7 kalenderdagen" eigenlijk "10 werkdagen" moet zijn, past de auteur beide regels aan en blijft de test groen. Een test die de implementatie naspeelt, legt niets vast. (2) Draait de test rond middernacht, dan kunnen de twee now()-aanroepen op verschillende dagen vallen. (3) LocalDate.now() gebruikt de standaardtijdzone van de JVM: in een container is dat vaak UTC, voor de merchant Europe/Amsterdam. Voorstel: LocalDate.now(clock) met een expliciete zone, en in de test Clock.fixed(...) met een harde verwachte datum (LocalDate.of(2026, 10, 13)). Let op: @InjectMocks geeft de Clock nu null mee. Construeer de service in de test zelf.

Regel 17, met 47 major Uit module 3. kafka.send binnen de @Transactional-methode is een dual write. Het event kan op de broker staan voordat de transactie commit. Faalt de commit daarna, dan boekt de ledger een chargeback af die niet bestaat (spookevent). Andersom blijft het record bestaan als de broker het bericht niet aanneemt: send is asynchroon, dus die fout bereikt deze transactie niet. Omdat de ledger op dit event geld afboekt, is blocker ook te verdedigen. De test op regel 47 legt de dual write juist vast: hij controleert dát er verstuurd wordt, niet wanneer. Voorstel: outbox-record in dezelfde transactie, of minimaal @TransactionalEventListener(AFTER_COMMIT) met de afweging uit module 3. Test dan het outbox-record, niet de send.

Regel 78 major Thread.sleep(2_000) om op @Async te wachten. Elke run kost twee seconden, ook als de verwerking na 50 ms klaar is. Op een drukke CI-agent kan de verwerking langer duren, en dan faalt de test af en toe. Voorstel: Awaitility, await().atMost(Duration.ofSeconds(10)).untilAsserted(() -> assertThat(chargebacks.count()).isEqualTo(1)). Die stopt zodra de assert slaagt. Kijk ook wat de test níet doet: een webhook die twee keer binnenkomt (de PSP levert at-least-once) staat nergens in de test.

Regels 50–60 en 70 geen probleem De afleider. Hier is verify wél de goede assert: acceptChargeback is een opdracht aan een extern systeem, en het enige zichtbare gevolg is dat de aanroep er wel of niet is. De tests zitten precies op de grens (1_499 en 1_500), gebruiken exacte argumenten en hebben namen die de regel beschrijven. Ze doden de grensmutant op <. @MockitoBean PspClient in de integratietest is een mock aan de systeemgrens, terwijl de database echt is (Postgres via Testcontainers). Dat is de goede verdeling. Een comment "geen mocks in een integratietest" kost je hier geloofwaardigheid.

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 1 · voorspellen

    De zwakke test uit het voorbeeld (verify(payments).findById(ID), isNotNull()) staat in de codebase. Er komen twee PR's binnen.

    A · lock tegen dubbele refunds

    var payment = payments
    .findByIdForUpdate(paymentId)
    .orElseThrow(...);

    B · rest "vereenvoudigd"

    long remaining =
    payment.amountMinor();

    Welke PR maakt de test rood?

    Antwoord tonen

    A, de verbetering. B, de bug, blijft groen.

    Waarom

    • A: findByIdForUpdate is niet gestubd, dus de mock geeft Optional.empty() (gemeten). De service gooit PaymentNotFound en de test faalt, terwijl het gedrag beter is geworden.
    • B: dit is R1 uit het diagram. Met 0 eerdere refunds is de rest gelijk aan het bedrag, en geen assert kijkt naar de waarde.

    In de review

    • Een test die bij een refactoring faalt en bij een bug niet, kost onderhoud zonder bescherming te bieden. Dat is het sterkste argument in een comment, sterker dan "te veel mocks".
  2. Vraag 2Doel 2 · verify of niet

    Twee verify-regels uit dezelfde testklasse.

    A · happy path

    service.refund(ID, 2_000);
verify(refunds).save(any());

    B · weigering

    assertThatThrownBy(() ->
    service.refund(ID, 2_001))
  .isInstanceOf(RefundExceeds…);
then(psp).shouldHaveNoInteractions();

    Welke van de twee test gedrag, en wat doe je met de andere?

    Antwoord tonen

    B test gedrag. A legt een implementatiedetail vast; vervang die door een assert op wat er is opgeslagen.

    Waarom

    • B: "er gaat geen geld naar buiten" kun je alleen zien aan het ontbreken van de aanroep naar het externe systeem. Dat is een uitgaande opdracht aan de systeemgrens.
    • A: save op je eigen repository is een tussenstap. Met any() slaagt de regel voor een refund met elk bedrag. Controleer het teruggegeven object, of gebruik een ArgumentCaptor of een fake en controleer de opgeslagen Refund op bedrag en referentie.

    Let op

    • Ook B is alleen sterk omdat hij op de grens zit (rest + 1 cent). Dezelfde regel met een refund van €1.000.000 doodt mutant M1 niet.
  3. Vraag 3Doel 3 · kiezen

    De fix uit het voorbeeld is gemerged. De repository ziet er zo uit; in de unit-test is sumRefunded gestubd op 8_000L, en alles is groen.

    @Query("select sum(r.amountMinor) from Refund r where r.paymentId = :paymentId")
long sumRefunded(UUID paymentId);

    Wat gebeurt er bij de eerste refund op een betaling in productie, en welke test had het gevangen?

    Antwoord tonen

    Een AopInvocationException: sum over nul rijen is null, en dat past niet in een long. Alleen een test tegen een echte database vangt dit.

    Waarom

    • SQL sum over een lege set geeft NULL, niet 0. Spring Data kan null niet als primitieve long teruggeven. Gemeten met @DataJpaTest (Boot 4.1.1, H2): Null return value from advice does not match primitive return type.
    • Een Mockito-mock van dezelfde methode geeft 0 terug. Elke unit-test, ook een goede, ziet dus het "juiste" getal.

    Beter

    • coalesce(sum(r.amountMinor), 0) (gemeten: 0), en een @DataJpaTest voor de query met drie gevallen: geen refunds, één refund, refunds van een andere betaling. Gebruik bij voorkeur Testcontainers met de productiedatabase. Vuistregel voor de review: zit de logica in de query, dan hoort de test bij de query.
  4. Vraag 4Doel 4 · tijd

    Een collega voegt een grenstest toe aan de oorspronkelijke service, die nog Instant.now() gebruikt. Lokaal is hij groen; in CI faalt hij af en toe.

    @Test
void allows_refund_on_the_last_moment_of_the_window() {
    var capturedAt = Instant.now().minus(Duration.ofDays(180));
    givenPayment(10_000, capturedAt, 0);
    assertThatCode(() -> service.refund(ID, 100)).doesNotThrowAnyException();
}

    Waarom faalt hij soms, en hoe maak je hem deterministisch?

    Antwoord tonen

    De service vraagt later opnieuw Instant.now(). Is de klok intussen een tik verder, dan ligt "nu" net voorbij het venster. Injecteer een Clock en test met Clock.fixed.

    Waarom

    • Hoe vaak het misgaat, hangt af van de resolutie van de systeemklok en de snelheid van de machine. Gemeten op een Windows-laptop: 133 van de 100.000 runs faalden. Op een andere machine kan dat veel vaker zijn. Daarom zie je het pas in CI.
    • Met Clock.fixed(NOW, UTC) in de service en NOW.minus(REFUND_WINDOW) in de test is de grens exact. Test beide kanten: precies 180 dagen mag, één seconde meer niet. Zo vang je ook het verschil tussen now.isAfter(end) en !now.isBefore(end): grens inclusief of exclusief.

    In de review

    • Een "flaky" test met now() erin is geen pech. Vraag om Clock, en niet om @RetryingTest of een marge van een minuut. Die verbergen het probleem.
  5. Vraag 5Doel 4 · zwaarte en comment

    De auteur van een refund-PR plakt een PIT-rapport (vereenvoudigd) en schrijft: "Line coverage 100%, dus volgens mij zijn we goed."

    RefundService.java
  24  changed conditional boundary           SURVIVED
  31  removed call to AuditLog::record       SURVIVED
  40  replaced return value with "" (toString)  SURVIVED

    Op welke mutant zet je een comment, met welke zwaarte, en wat schrijf je?

    Antwoord tonen

    Regel 24 als major (de restcontrole). Bij regel 31 een vraag, afhankelijk van of de audit verplicht is. Regel 40 laat je gaan.

    Waarom

    • 24: geen test raakt de grens van de bedragscontrole. Precies-de-rest en rest + 1 cent ontbreken.
    • 31: is de audit-trail een compliance-eis, dan is een stil verdwenen record een echt risico, en is een test met een fake AuditLog op zijn plaats. Is het alleen een debug-spoor, dan niet.
    • 40: een overlevende mutant op toString beschermt niemand. 100% mutation score is geen doel.

    In de review

    issue: PIT laat zien dat de grens van de restcontrole (r. 24) niet getest is: > → >= overleeft, dus een refund van precies het restbedrag kan stuk gaan zonder dat een test faalt. Kun je twee tests toevoegen: precies de rest (mag) en rest + 1 cent (weigert, en geen PSP-aanroep)? question: is AuditLog.record (r. 31) een compliance-eis? Dan wil ik er ook een test op.

Verder lezen

  • PIT, Mutation operators: welke mutators in de standaardset zitten (Conditionals Boundary, Math, Negate Conditionals, Void Method Calls, de return-mutators) en welke optioneel zijn. Daarnaast Maven quickstart voor scmMutationCoverage, withHistory en mutationThreshold.
  • Spring Boot Reference, Testing Spring Boot Applications: de secties "Mocking and Spying Beans" (@MockitoBean) en "Auto-configured Tests" (slices zoals @WebMvcTest en @DataJpaTest).
  • Spring Boot Reference, Testcontainers: @ServiceConnection, zodat een test de echte database gebruikt zonder handmatige configuratie.
  • Vladimir Khorikov, Unit Testing Principles, Practices, and Patterns (Manning): de hoofdstukken over mocks en testfragiliteit, en over observable behavior tegenover implementatiedetails. Daar komt het onderscheid tussen een uitgaande opdracht aan de systeemgrens en interne communicatie vandaan.
