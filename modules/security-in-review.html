Module 8 · D9 Security

Security in review

Een ingelogde merchant die met een ander ID in de URL de betalingen van een concurrent leest, of de uitbetalings-IBAN van een andere merchant wijzigt. Dat is geen exotische aanval: het staat bovenaan de OWASP API Top 10, en de code komt door elke test. Vaak is de reviewer de enige die het ziet.

Tijd 45 minStack Java 25 · Spring Boot 4 · Spring Security 7

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Een endpoint valt onder .anyRequest().authenticated() en de methode heeft @PreAuthorize("hasRole('MERCHANT')"). Wat wordt er dan nog niet gecontroleerd?
  2. Met setParameter("ref", input) en met "'" + input + "'" vergelijkt de database dezelfde tekst. Waarom is het eerste veilig en het tweede niet?
  3. Wat staat er in de log na log.info("Nieuwe kaart: {}", card) als card een record is?

Wat er onder de motorkap gebeurt

Drie vragen, drie plekken

Elke request beantwoordt drie verschillende vragen. Ze worden op verschillende plekken beantwoord, en alleen de eerste twee doet Spring Security voor je.

  • Authenticatie: wie ben je? De SecurityFilterChain leest een sessie, Basic-header of JWT en zet een Authentication in de SecurityContext. Uitkomst: "dit is Alice van merchant M-100".
  • Autorisatie op functieniveau: mag deze rol dit endpoint aanroepen? authorizeHttpRequests per URL, of @PreAuthorize("hasRole('MERCHANT')") per methode. Uitkomst: "merchants mogen betalingen bekijken".
  • Autorisatie op objectniveau: mag déze gebruiker déze betaling zien? Dat kan Spring Security niet weten. Het ID komt uit de request, de eigenaar staat in jouw database. Deze check bestaat alleen als iemand hem schrijft: in de query, of in een expressie die het object kent.

Elke waarde in de request die een record aanwijst, is invoer van de aanroeper: een path variable, een query parameter, een veld in de body. Dat geldt ook voor een merchantId in de URL. "De frontend stuurt alleen eigen ID's mee" zegt niets: een client stuurt wat hij wil.

Concatenatie maakt invoer tot code

JPQL is een taal. em.createQuery(String) geeft de hele string aan de HQL-parser van Hibernate, en alles in die string wordt syntaxis. Plak je invoer erin, dan doet die invoer mee aan het parsen: een enkele quote sluit de string-literal af en de rest wordt query. Met parameter binding wordt de querytekst geparsed met :reference als placeholder; de waarde gaat los daarvan als JDBC-bindparameter naar de database en wordt nooit als query gelezen. Wat je niet kunt binden (een kolomnaam, asc/desc), moet uit een vaste lijst komen.

Wat er naar buiten lekt

Invoer komt binnen via de request; data gaat naar buiten via kanalen die niemand als API ziet:

  • Logs. Die gaan naar een centraal platform met meer lezers en een langere bewaartermijn dan je database. Een PAN of CVC in een log haalt dat hele platform binnen de PCI DSS-scope; een IBAN met naam is persoonsgegeven onder de AVG.
  • toString() van een record bevat elke component: AddCard[pan=4111111111111111, expiry=…, cvc=…]. Een {} in een logregel, een "…" + obj in een exception of de foutmelding van Collectors.toMap bij een dubbele sleutel (zie F1) gebruikt die toString().
  • Exception-messages worden gelogd door wie ze vangt, komen in je error tracker, en soms in de response.
  • Foutresponses. Spring Boot is standaard zuinig: zonder configuratie bevat de JSON van /error alleen timestamp, status, error en path. In Boot 4 heten de knoppen spring.web.error.include-message, include-stacktrace (standaard never) en include-exception (standaard false). Maar elke eigen @ExceptionHandler die e.getMessage() in een ProblemDetail stopt, omzeilt die standaard. En met spring.mvc.problemdetails.enabled=true gaat de reason van een ResponseStatusException als detail naar de client.

Geverifieerd: alle gedragsclaims in deze module zijn nagespeeld met Spring Boot 4.1.1 (Spring Security 7.1.1, Hibernate 7.4.5, H2), via echte HTTP-calls met Basic-authenticatie op JDK 25. De geconcateneerde query gaf met de invoer uit paneel B alle vier de testbetalingen van beide merchants terug; de geparametriseerde versie []. Een DataIntegrityViolationException-message bevatte de SQL, de constraintnaam en de dubbele IBAN. De oude property server.error.include-message=always werd in Boot 4.1.1 stil genegeerd; spring.web.error.include-message=always werkte.

Oplossingen en hun prijs

Voor de ontbrekende eigenaarscheck:

A · Eigenaar in de query

findByIdAndMerchantId(id, user.merchantId()) en 404 als hij leeg is. Andermans betaling en een niet-bestaande betaling zijn voor de aanroeper niet te onderscheiden. Eén query, geen extra configuratie. Prijs: elke nieuwe repository-methode moet de scope weer meekrijgen. Het volgende endpoint vergeet het net zo makkelijk.

B · @PostAuthorize op het resultaat

@PostAuthorize("returnObject.merchantId() == authentication.principal.merchantId"). Declaratief, en de regel staat bij de methode. Prijs: werkt alleen met @EnableMethodSecurity; de security-starter zet dat niet aan, en zonder wordt de annotatie stil genegeerd. Het is een proxy, dus een aanroep via this slaat de check over (zie module 1). De methode draait eerst helemaal, met eventuele side effects. En de aanroeper krijgt 403 voor een bestaande en 404 voor een niet-bestaande betaling: zo kun je raden welke ID's bestaan.

C · Scoping centraal regelen

Laat de tenant uit de query niet aan elke developer over: Hibernate @TenantId of @Filter, of row-level security in PostgreSQL. Prijs: meer infrastructuur en een plek waar je ook bewust ín moet kunnen (backoffice, batches). Maar een vergeten check is dan geen lek meer. Bij een multi-tenant platform op termijn de juiste plek.

Voor de injectie is er geen afweging: parameters. Een derived query (findByMerchantIdAndMerchantReference) is nog korter; voor dynamische filters is er de Criteria API of een Spring Data Specification. Zelf quotes escapen (reference.replace("'", "''")) is geen fix: dan hangt je veiligheid af van jouw kennis van de grammatica van elke querytaal en database die je ooit gebruikt.

De toString()-override is de belangrijkste regel: die beschermt ook de volgende developer die card in een log of exception zet. De betere oplossing ligt nog een stap verder: laat het PAN je backend helemaal niet bereiken, met hosted fields of versleuteling in de browser door de PSP. Wat je niet ontvangt, kun je niet lekken, en je PCI-scope wordt veel kleiner.

Wanneer het géén probleem is

  • findById zonder eigenaarscheck waar de aanroeper geen eindgebruiker is. Een batchjob, een Kafka-consumer die eigen events verwerkt, een interne service-to-service-call. Het ID komt dan niet uit onvertrouwde invoer.
  • Een backoffice-rol die alles mag zien, zoals hasRole('SUPPORT') op een supportscherm. Dat is een bewuste keuze. Controleer wel dat de rolcheck er echt staat (en dat method security aan staat), en vraag naar een audit log.
  • Scoping die al centraal geregeld is: @TenantId, een Hibernate-filter of row-level security. Eis dan niet in elke query nog een merchantId, maar controleer dat het nieuwe pad er echt onder valt.
  • Concatenatie van constanten of een whitelist: "order by p." + sort.property waarbij sort een enum is. Spring zet de requestparameter om naar de enum; vrije tekst geeft een 400 en bereikt de query nooit.
  • like concat('%', :q, '%') met een parameter. Geen injectie. Dat % en _ als wildcard werken is hooguit een functioneel punt.
  • Loggen van ID's en gemaskeerde waarden: betaling-ID, PSP-referentie, de laatste vier cijfers van een kaart of IBAN. Dat is wat je in een incident nodig hebt.
  • Validatiefouten over de eigen invoer ("bedrag moet groter zijn dan 0") naar de client. Het lek gaat over interne details en data van anderen.

Zwaarte: blocker als iemand data van een andere tenant kan lezen of een geldstroom kan wijzigen, als onvertrouwde invoer in een query wordt geplakt, of als PAN, CVC, wachtwoord of volledig token in een log of response belandt · major bij IBAN of naam in de log, interne details (SQL, stacktrace, PSP-meldingen) in een response, of een check die alleen werkt zolang niemand iets via this aanroept · minor bij een 403/404-verschil dat bestaan verraadt, waar dat geen geheim is · laat gaan bij gewhiteliste concatenatie en gemaskeerde logging.

Sterk

Antwoordsleutel tonen

Regels 2, 14–18 blocker Objectniveau-autorisatie ontbreekt. merchantId komt uit de URL en @PreAuthorize controleert alleen de rol. Elke MERCHANT_ADMIN van welke merchant dan ook kan de uitbetalings-IBAN van een andere merchant zetten; de volgende uitbetaling van die merchant gaat naar zijn rekening. Regel 25 doet het in dezelfde PR wél goed, en dat verschil is je beste argument. Voorstel: dezelfde voorwaarde (#merchantId == authentication.principal.merchantId), of beter: merchantId uit de principal halen en uit de URL schrappen, zodat er niets meer te vergelijken valt.

Regels 17 en 38 major {} met body roept de toString() van het record aan: IBAN en naam van de rekeninghouder staan in de log, bij elke wijziging. Persoonsgegevens in een systeem met bredere toegang en langere bewaartermijn, en precies de gegevens waar fraude om draait. Voorstel: log merchantId en de laatste vier tekens van de IBAN, en override toString() in ChangePayoutAccount zodat de volgende logregel ook veilig is.

Regels 18–20 major Uit module 3. Dual write: change commit in zijn eigen transactie, daarna pas kafka.send. Faalt de send of crasht de pod ertussen, dan is de rekening gewijzigd zonder bevestigingsmail en zonder 48-uurshold. Een stille wijziging van de uitbetalingsrekening is precies wat een aanvaller wil; samen met de blocker hierboven is dit ook verdedigbaar als blocker. Voorstel: het event via een outbox in dezelfde transactie als de wijziging. (Klein punt: Instant.now() zonder Clock.)

Regels 31–33 major e.getMessage() van een DataIntegrityViolationException gaat naar de client. In onze test bevatte die de SQL-insert, de tabel- en constraintnaam en de dubbele IBAN: schema-informatie naar buiten, en een bevestiging dat die IBAN al bij een andere merchant hoort. Voorstel: map de bekende constraint naar een domeinmelding ("deze rekening kan niet worden gebruikt"), log de exception aan de serverkant, en stuur een generieke detail mee.

Regels 57–61 geen probleem De afleider: een string plakken in een JPQL-query. Maar sort.property komt uit een enum met twee vaste waarden. Spring zet de requestparameter om naar PaymentSort; vrije tekst geeft een 400 voordat de query bestaat (in onze test: sort=amount desc, p.id gaf 400). Dit is de whitelist die je wilt voor wat niet te binden is, en merchantId is netjes een parameter. Wie hier "SQL-injectie" schrijft, kost de auteur tijd en zichzelf geloofwaardigheid.

Bonus vraag setMaxResults(200) zonder paginering: ziet een merchant met meer betalingen alleen de nieuwste 200, en weet de UI dat?

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 1 · voorspellen

    Twee varianten van het detail-endpoint. Alice (M-100) vraagt eerst een bestaande betaling van M-200 op, daarna een ID dat niet bestaat.

    A · controle op het resultaat

    @PostAuthorize(
  "returnObject.merchantId() == authentication.principal.merchantId")
PaymentView get(@PathVariable UUID id) {
    return PaymentView.from(payments.findById(id)
        .orElseThrow(() -> new PaymentNotFoundException(id)));
}

    B · eigenaar in de query

    PaymentView get(@AuthenticationPrincipal MerchantUser user,
                @PathVariable UUID id) {
    return PaymentView.from(payments
        .findByIdAndMerchantId(id, user.merchantId())
        .orElseThrow(() -> new PaymentNotFoundException(id)));
}

    Welke statuscodes krijgt Alice in A en in B?

    Antwoord tonen

    A: 403 voor de betaling van M-200 en 404 voor het onbekende ID. B: twee keer 404.

    Waarom

    • In A draait de methode eerst. Bestaat de betaling, dan faalt de expressie daarna en gooit Spring Security een AuthorizationDeniedException: 403. Bestaat hij niet, dan komt de 404 uit de methode zelf, nog voor de check.
    • In B vindt de query in beide gevallen niets.

    Let op

    • Met A kan Alice dus vaststellen welke ID's bestaan. Bij betalingen is dat meestal een minor, bij bijvoorbeeld "bestaat er een account met dit e-mailadres" kan het zwaarder wegen. En A werkt alleen als @EnableMethodSecurity aan staat.
  2. Vraag 2Doel 1 · herkennen

    Een collega voegt een bulk-endpoint toe dat de bestaande, goed beveiligde methode hergebruikt. @EnableMethodSecurity staat aan.

    @PutMapping("/payout-accounts")
@Transactional
public void changeAll(@RequestBody List<Change> changes) {
    changes.forEach(c -> this.change(c.merchantId(), c.body()));
}

@PreAuthorize("hasRole('MERCHANT_ADMIN') and #merchantId == authentication.principal.merchantId")
public void change(String merchantId, ChangePayoutAccount body) { ... }

    Wordt de @PreAuthorize op change toegepast?

    Antwoord tonen

    Nee. Elke ingelogde gebruiker kan via changeAll de rekening van elke merchant wijzigen.

    Waarom

    • Method security is, net als @Transactional, een interceptor op de Spring-proxy. this.change(...) loopt niet via de proxy, dus de check wordt nooit uitgevoerd. Hetzelfde mechanisme als in module 1.
    • In onze test wijzigde een gebruiker zonder rol en van een andere merchant zo de IBAN: 200.

    In de review

    issue (blocking): changeAll roept change via this aan, dus de @PreAuthorize op change wordt overgeslagen. Elke ingelogde gebruiker kan zo de uitbetalingsrekening van elke merchant zetten. Voorstel: haal merchantId uit de principal in plaats van uit de body, of zet de autorisatie in een aparte bean die je via de proxy aanroept.

    Zoeken op een deel van de referentie, binnen de eigen merchant.

    Welke variant is te injecteren, en wat blijft er bij de andere nog over om op te letten?

    Antwoord tonen

    A is te injecteren, ook al is merchantId netjes een parameter. B is veilig; alleen werken % en _ in q nog als wildcard.

    Waarom

    • Eén geplakte waarde is genoeg. In A staat q in de querytekst; een quote sluit de literal en de rest wordt query. Dat er elders parameters staan, verandert daar niets aan.
    • In B is q een bindparameter en blijft hij een waarde. In onze test vond q=D_ zowel ORD-9 als ORD_10: de underscore matcht elk teken. Dat is functioneel, geen lek: de merchantfilter blijft staan.

    In de review

    • Bij B hooguit een nit of vraag: moeten wildcards letterlijk zijn (dan escapen met een escape-clausule), en is een like '%…' zonder index acceptabel op deze tabel?
  4. Vraag 4Doel 3 · voorspellen

    Een validatie gooit deze exception. Er is geen eigen @ExceptionHandler voor. Een PR in Boot 4 zet spring.mvc.problemdetails.enabled=true aan, "omdat RFC 9457 netter is".

    throw new ResponseStatusException(HttpStatus.BAD_REQUEST,
        "IBAN " + iban + " is al gekoppeld aan merchant " + owner.merchantId());

    Wat ziet de client vóór en na die PR?

    Antwoord tonen

    Vóór: een 400 met alleen timestamp, status, error en path. Na: een ProblemDetail met de volledige reason als detail, dus inclusief de andere merchant.

    Waarom

    • Zonder Problem Details handelt de /error-afhandeling van Boot het af, en spring.web.error.include-message staat standaard op never.
    • Met Problem Details maakt Spring MVC zelf de response en gebruikt het de reason als detail. De include-message-instelling speelt dan geen rol.

    Let op

    • De echte fout zit in de exception: die verraadt dat een IBAN bij een andere merchant hoort. De configwijziging maakt hem alleen zichtbaar. Reviewregel: een reason is tekst voor de client, schrijf hem ook zo.
    • In Boot 4 heten de properties spring.web.error.*. Een overgenomen server.error.include-message werd in onze test stil genegeerd.
  5. Vraag 5Doel 4 · zwaarte en comment

    De auteur reageert op je opmerking: "debug staat in productie uit, dus dit wordt nooit gelogd."

    record AddCard(String pan, YearMonth expiry, String cvc, String holderName) {}

log.debug("Received card for merchant {}: {}", merchantId, card);

    Klopt het argument, en welke zwaarte geef je?

    Antwoord tonen

    Technisch klopt het voor vandaag, en toch blijft het een blocker: het PAN en de CVC zijn één configwijziging van de log verwijderd.

    Waarom

    • Klopt: SLF4J roept toString() niet aan als het niveau uit staat. In onze test bleef een toString()-teller op 0 bij debug en ging naar 1 bij warn.
    • Maar debug gaat juist aan tijdens een incident, vaak tijdens runtime via het loggers-endpoint van Actuator, en staat op test- en acceptatieomgevingen vaak al aan.
    • Het echte probleem is de toString() van het record. Die lekt ook via exceptions, toMap-meldingen en de volgende log.info.

    In de review

    issue (blocking): klopt dat deze regel nu niet logt, maar debug zetten we tijdens incidenten aan, en dan staan PAN en CVC in Elastic. Dat haalt het logplatform binnen de PCI-scope. Voorstel: override toString() in AddCard met een gemaskeerd PAN (laatste vier) en zonder CVC, en log hier alleen merchantId en last4.
