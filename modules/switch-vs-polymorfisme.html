Module 6b · D1 · D3

Switch vs polymorfisme

Een nieuwe betaalmethode komt erbij, de PR raakt twee bestanden, alle tests zijn groen. Het derde bestand, dat niet in de diff staat, eindigt met return BigDecimal.ZERO, en drie weken lang rekent het platform geen cent fee op elke Wero-betaling. Waar een nieuwe variant moet landen, en of de compiler je dan helpt, is een ontwerpkeuze. In de review moet je die keuze kunnen zien en wegen.

Tijd 45 minStack Java 25 (alle taalgedrag gedraaid op JDK 25.0.4)Spoor tussen ontwerp (D3) en spoor F

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Je voegt een record toe aan een sealed interface. Welke switch-en in de codebase geven een compileerfout, en welke niet?
  2. Wat doet een default-tak in een switch die al alle permitted subtypes afdekt: vandaag, en op de dag dat er een subtype bijkomt?
  3. Een module met een exhaustive switch wordt níet opnieuw gecompileerd nadat er een subtype is bijgekomen. Wat gebeurt er als dat nieuwe type langskomt?

Wat er onder de motorkap gebeurt

Zet je betaalmethodes als rijen en de operaties erop als kolommen: fee berekenen, refundroute kiezen, settlementvertraging, risicoscore. Elke cel is een stukje logica. Er zijn twee manieren om die tabel in code te snijden, en elke manier maakt één richting van uitbreiden goedkoop en de andere duur. Dat heet het expression problem, en het is de echte vraag achter elke "maak hier Strategy van"-comment.

  • Polymorfisme snijdt per rij. Elk type is een klasse met een methode per operatie. Een nieuw type is één nieuwe klasse, en de compiler eist dat elke abstracte methode wordt geïmplementeerd. Een nieuwe operatie betekent: elke klasse openen. En het type moet alles weten wat die operaties nodig hebben: tarieven, refund-rails, risicoregels.
  • Een switch over een sealed type snijdt per kolom. Elke operatie is één functie, in de module die haar bezit. Een nieuwe operatie is één nieuwe functie. Een nieuw type betekent: elke switch moet mee. Dat klinkt duur, maar de compiler wijst ze allemaal aan, mits je hem dat laat doen.

Dat laatste is het mechanisme waar het in een review om draait. Bij sealed interface PaymentMethod permits Card, Ideal, SepaDebit kent javac de volledige lijst subtypes. Een switch-expressie, of een switch-statement met patterns, moet exhaustive zijn: elk permitted subtype moet gedekt zijn door een case zonder guard. Het controleren gebeurt tijdens het compileren. Tijdens runtime test de gecompileerde code de cases van boven naar beneden (via invokedynamic naar SwitchBootstraps.typeSwitch; zichtbaar met javap -c), en de eerste case waarvan pattern én guard passen wint. Voor het geval dat er na het compileren toch een onbekend type langskomt, zet de compiler zelf een verborgen tak neer die MatchException gooit.

Een default-tak vervangt die verborgen tak. Dat is het hele verschil: met default is de switch altijd exhaustive, ook na het toevoegen van een subtype, en de compiler heeft niets meer te melden.

Wat de compiler wel en niet controleert

Elke regel hieronder is gecompileerd met javac -Xlint:all op JDK 25.0.4. De meldingen zijn letterlijk overgenomen.

SituatieWat er gebeurt
switch-expressie over sealed type, één subtype vergetenFout: the switch expression does not cover all possible input values
switch-statement met type patterns, subtype vergetenFout: the switch statement does not cover all possible input values
Alleen cases mét guard voor Card (case Card c when …), geen kale case CardDezelfde "does not cover"-fout. Guards tellen niet mee voor exhaustiveness; de compiler weet niet dat jouw twee guards samen alles afdekken.

Twee guards voor Card die elkaar overlappen, in de verkeerde volgordeCompileert zonder waarschuwing. Dominantie geldt alleen voor cases zonder guard. Of when region == EEA vóór of na when scheme == AMEX staat, is jouw verantwoordelijkheid.
Exhaustive switch over sealed type, plús een overbodige defaultCompileert zonder fout of waarschuwing. Pas op de dag dat er een subtype bijkomt, merk je dat de controle uitstaat: dan merk je juist niets.
Enum-switch-expressie, constante vergetenFout: the switch expression does not cover all possible input values
Enum-switch-statement (pijl- of dubbelepuntvorm), constante vergetenCompileert. Een "gewone" switch-statement over een enum hoeft niet exhaustive te zijn (JLS §14.11.2, om oude code te laten compileren). De nieuwe constante doet stil niets. Voeg je case null toe, dan wordt het een enhanced switch en moet hij wél exhaustive zijn.
null als selectorNullPointerException, ook mét default: default vangt geen null. Alleen een expliciete case null (of case null, default) doet dat.
Record zonder implementatie van de abstracte methode van zijn sealed interfaceFout: PricedWero is not abstract and does not override abstract method fee(BigDecimal) in PricedMethod. Bij polymorfisme dwingt de compiler het nieuwe type af.

Geverifieerd: aparte compilatie. Een hiërarchie Card, Ideal en een enum Kind { CARD, IDEAL } gecompileerd, samen met een klasse Fees met vier varianten. Daarna Wero en WERO toegevoegd en alleen de hiërarchie opnieuw gecompileerd. Resultaat voor de nieuwe waarde: exhaustive sealed switch → java.lang.MatchException (zonder message); switch met default → stil de default-tak (0.00); enum-switch-expressie → MatchException; enum-switch-statement → stil overgeslagen. Na hercompilatie van Fees gaven beide expressies de compileerfout. Bij een multi-module build (aparte jars per team) is dit geen theorie: de module die je niet opnieuw bouwt, valt bij runtime om, en dat is nog de goede uitkomst.

"Gebruik een enum" of "maak er Strategy van" zijn allebei verdedigbare reacties. Ze lossen alleen niet hetzelfde op. Hieronder dezelfde fee-regel op vijf manieren; alle vijf zijn gecompileerd en gedraaid op JDK 25.

Vijf varianten voor dezelfde regel

A · instanceof-keten

if (method instanceof Card card) {
    if (card.scheme() == Scheme.AMEX) return percent(amount, "2.90");
    return card.issuerRegion() == Region.EEA
            ? percent(amount, "0.30") : percent(amount, "1.90");
} else if (method instanceof Ideal) {
    return new BigDecimal("0.29");
} else if (method instanceof SepaDebit) {
    return new BigDecimal("0.35");
}
throw new IllegalArgumentException("Onbekende betaalmethode: " + method);

Beter dan strings: typen in plaats van tekst, en de laatste regel gooit in plaats van €0 terug te geven. Prijs: de compiler controleert niets. Wero geeft IllegalArgumentException tijdens runtime (nagespeeld), in productie, bij de eerste betaling. Een if-keten over een sealed type is in Java 25 bijna altijd een switch die nog niet is omgeschreven.

B · Enum + switch-expressie

return switch (method.type()) {
    case CARD -> method.scheme() == Scheme.AMEX ? percent(amount, "2.90")
            : method.issuerRegion() == Region.EEA ? percent(amount, "0.30")
            : percent(amount, "1.90");
    case IDEAL -> new BigDecimal("0.29");
    case SEPA_DD -> new BigDecimal("0.35");
    case WERO -> new BigDecimal("0.20");
};

Exhaustive: een nieuwe constante zonder case is een compileerfout. Prijs: een enum is een label zonder eigen data. scheme en issuerRegion blijven nullable velden naast het label, dus onmogelijke toestanden blijven mogelijk. En de bescherming geldt alleen voor de expressie: schrijft iemand ergens een switch-statement over dezelfde enum, dan controleert de compiler niets.

C · Strategy + factory

interface FeeRule {
    MethodType type();
    BigDecimal feeFor(PaymentMethod method, BigDecimal amount);
}

@Component
class FeeRules {
    private final Map<MethodType, FeeRule> byType;

    FeeRules(List<FeeRule> rules) {   // Spring injecteert alle FeeRule-beans
        byType = rules.stream().collect(toMap(FeeRule::type, identity(),
                (a, b) -> { throw new IllegalStateException("Dubbele FeeRule voor " + a.type()); },
                () -> new EnumMap<>(MethodType.class)));
        var missing = EnumSet.complementOf(EnumSet.copyOf(byType.keySet()));
        if (!missing.isEmpty()) throw new IllegalStateException("Geen FeeRule voor " + missing);
    }
}

Een nieuw type is een nieuwe bean; niemand hoeft een bestaand bestand te openen. Elke regel kan eigen dependencies krijgen (een tarieventabel, een FX-service). Prijs: de compiler ziet niets. Zonder de dekkingscheck in de constructor faalt een vergeten regel pas bij de eerste Wero-betaling; mét die check faalt de applicatie bij het opstarten (nagespeeld: IllegalStateException: Geen FeeRule voor [SEPA_DD, WERO]). Dat is het beste wat je hier kunt krijgen, en die check schrijft bijna niemand. Plus: vier klassen en een interface voor wat een tabel van vier regels is.

D · Polymorfe methode op het type

public sealed interface PaymentMethod permits Card, Ideal, SepaDebit, Wero {
    BigDecimal fee(BigDecimal amount);
    RefundRoute refundRoute();
    Period settlementDelay();
}

Een nieuw type móét elke methode implementeren; de compiler dwingt het af. Prijs: elke nieuwe operatie opent elke record, en het domeintype trekt kennis van drie teams naar zich toe. Zodra de fee afhangt van het merchantcontract, wordt het fee(amount, contract, fxRates), en dat kan een record niet laten injecteren. Polymorfisme is hier sterk zolang de operatie intrinsiek is aan het type (Money.add, Iban.isValid), niet als het beleid van iemand anders is.

E · Sealed interface + records + pattern-matching-switch

public sealed interface PaymentMethod permits Card, Ideal, SepaDebit, Wero {}
public record Card(Scheme scheme, Region issuerRegion) implements PaymentMethod {}
public record Ideal(String bic) implements PaymentMethod {}
public record SepaDebit(String mandateId) implements PaymentMethod {}
public record Wero(String walletId) implements PaymentMethod {}

// FeeCalculator.java, in de pricing-module
public BigDecimal feeFor(PaymentMethod method, BigDecimal amount) {
    return switch (method) {
        case Card(var scheme, _) when scheme == Scheme.AMEX -> percent(amount, "2.90");
        case Card(_, var region) when region == Region.EEA -> percent(amount, "0.30");
        case Card _ -> percent(amount, "1.90");
        case Ideal _ -> new BigDecimal("0.29");
        case SepaDebit _ -> new BigDecimal("0.35");
        case Wero _ -> new BigDecimal("0.20");
    };
}

Elke methode draagt alleen haar eigen data; een iDEAL-betaling met een scheme bestaat niet meer. De operatie blijft in de module die haar bezit. Een nieuw record geeft een compileerfout in elke switch die het nog niet kent. Record patterns halen de componenten eruit, _ (unnamed pattern, definitief sinds Java 22) zegt "dit veld doet er niet toe", en de guards lezen als de tarieftabel. Prijs: de volgorde van de guards is semantiek (zie hieronder), en de bescherming werkt alleen zolang niemand een default toevoegt.

De vraag is dus niet "switch of polymorfisme", maar: wat groeit hier, en wie bezit de logica? Betaalmethodes komen er een of twee per jaar bij; operaties erop komen er elk kwartaal bij, en ze horen bij verschillende teams. Dat is kolomwerk: variant E. Neem nu de koppelingen met acquirers. Daar komen elk kwartaal nieuwe bij, de set operaties staat vast (authorise, capture, refund), en elke koppeling heeft een eigen HTTP-client, eigen credentials en eigen foutcodes. Dat is rijwerk: een interface met een Spring-bean per acquirer.

public interface AcquirerConnector {
    AcquirerId id();
    AuthorisationResult authorise(AuthorisationRequest request);
    CaptureResult capture(CaptureRequest request);
    RefundResult refund(RefundRequest request);
}

@Component
class AcquirerRegistry {
    private final Map<AcquirerId, AcquirerConnector> byId;

    AcquirerRegistry(List<AcquirerConnector> connectors) {   // dubbele id: faalt bij opstarten
        this.byId = connectors.stream().collect(toUnmodifiableMap(AcquirerConnector::id, identity()));
    }
}

Een sealed AcquirerConnector met een switch in een centrale service zou die service afhankelijk maken van elke acquirer-client. Daar is de open interface juist goed, en dat de compiler een vergeten acquirer niet vindt, maakt niet uit: er is geen switch die hem kan vergeten.

Twee details die in bijna elke PR terugkomen

Guards worden van boven naar beneden getest. In variant E staat de Amex-regel bewust vóór de EER-regel. Draai je ze om, dan compileert het nog steeds, zonder waarschuwing, en een EER-Amex-betaling van €200 kost €0,60 in plaats van €5,80 (nagespeeld). De compiler meldt alleen dominantie door een case zonder guard; overlappende guards zijn voor de reviewer. Lees een guarded switch daarom als een beslistabel en vraag bij elke rij: welke input die hieronder bedoeld is, wordt hier al gevangen?

Aan de rand blijft één string-switch, en dáár hoort default. De database en de API kennen geen sealed types. De mapper van entity naar domein switcht op de string, en daar is default -> throw new UnknownPaymentMethodException(type) precies goed: een string is een open type, er bestaat geen exhaustive switch over. Het verschil met de fout hierboven: deze default gooit, op één plek, aan de grens, in plaats van een bedrag te verzinnen midden in de logica.

Wanneer het géén probleem is

  • Meerdere switches over hetzelfde sealed type. Dat lijkt op "dezelfde switch op drie plekken", de klassieke OCP-smell. Maar als elke switch een andere operatie is, in de module die haar bezit, en geen ervan een default heeft, dan is dit het ontwerp en niet het probleem. De compiler houdt ze synchroon. De smell is pas echt als het drie keer dezelfde vraag is ("is dit een kaart met 3DS?") of als de switches op een string of een niet-sealed type staan.
  • Eén kleine, stabiele switch in één methode. switch (scheme) { case VISA -> "Visa"; … } voor een weergavenaam: een Strategy-hiërarchie daarvoor is speculatieve generaliteit.
  • Een enkele instanceof voor een vraag over één type. if (method instanceof PayByBank p) om alleen voor Pay by Bank iets extra's te doen, is geen keten. Alle andere types doen niets, en dat blijft zo als er een type bijkomt.
  • default over een open type. Strings, getallen, een niet-sealed interface, een enum van een externe partij die je niet beheert (bijv. een gegenereerde enum uit een API-spec): daar is een exhaustive switch niet mogelijk of niet zinvol, en is default -> throw de juiste keuze.
  • Strategy waar de set echt open is. Acquirer-koppelingen, exportformaten per klant, plug-ins van andere teams: types groeien, operaties staan vast, en elke implementatie heeft eigen dependencies.
  • Polymorfisme voor intrinsiek gedrag. Money.add, Iban.checksumValid(): hoort bij het type, heeft geen externe dependencies, en geen ander team bezit het.

Zwaarte: blocker als een nieuw type nu al stil in een fallback valt die geld, routering of compliance raakt (fee €0, refund via het verkeerde rail, overgeslagen controle) · major bij een guard-volgorde die voor een deel van de input het verkeerde resultaat geeft, of bij een nieuwe default over een sealed type in logica die geld raakt, ook als hij vandaag nog klopt · minor bij een instanceof-keten of default -> throw over een sealed type (faalt luid, maar pas tijdens runtime), en bij Strategy + factory voor twee vaste gevallen · nit of laat gaan: switch of polymorfisme als smaakvraag, zonder dat je kunt zeggen wat er groeit.

Zo schrijf je het op

Zwak

Switch op type is een OCP-schending. Graag Strategy-pattern gebruiken.

Een regel uit een boek, geen gevolg. De auteur bouwt vier klassen en een factory, de fee-fout in FeeCalculator blijft liggen, en de volgende betaalmethode wordt alsnog vergeten, nu in een ontbrekende bean.

Sterk

issue (blocking) FeeCalculator.feeFor (niet in deze PR) eindigt met return BigDecimal.ZERO, dus elke Wero-betaling krijgt €0,00 fee. Lokaal nagespeeld met type = "WERO". Ook SettlementCalendar valt via default naar de kaartvertraging.

Voorstel: voor deze PR: Wero expliciet toevoegen in beide plekken, en de fallback in FeeCalculator laten gooien in plaats van 0 teruggeven. Als vervolg: PaymentMethod sealed maken met een record per methode en de drie switches zonder default schrijven. Dan is de volgende methode een compileerfout op elke plek die hem nog niet kent, in plaats van een maandfactuur die niet klopt.

Antwoordsleutel tonen

Regel 76 blocker Niet in de PR veranderd, en juist daarom het belangrijkste. routeFor dekte al alle drie de subtypes af, en de default stond er "voor de zekerheid". Zo'n overbodige default compileert zonder waarschuwing (nagespeeld). Nu valt PayByBank erin en gaat elke Pay-by-Bank-refund naar SCHEME_REFUND: een kaartrefund voor een betaling zonder kaart. Op zijn best faalt elke refund bij het scheme, op zijn slechtst blijft hij hangen in een status die niemand monitort. Dit is precies de plek waar "de compiler wees alle plekken aan" niet klopt: de compiler wijst geen switch aan die een default heeft. Haal de default weg (nagespeeld: dan geeft regel 73 the switch expression does not cover all possible input values) en voeg case PayByBank _ -> RefundRoute.SEPA_CREDIT_TRANSFER toe. Het is ook een goede gewoonte om bij een nieuw subtype in de PR te zoeken op default in alle switches over dat type.

Regels 63–64 blocker Uit F3 (Optional en afwezigheid). orElse evalueert zijn argument altijd, dus configs.save(...) draait bij elke refund, ook als de config bestaat. Met de unique constraint op country faalt elke tweede Pay-by-Bank-refund per land (nagespeeld met een stub-repository: refund 1 slaagt, refund 2 geeft een duplicate-key-fout, 2 saves). Zonder die constraint krijg je dubbele rijen en daarna een fout op findByCountry. Gebruik orElseGet(() -> configs.save(...)), en vraag of een ontbrekende config niet gewoon een fout moet zijn in plaats van een stil aangemaakte default.

Regels 14–15 major De guard voor zakelijke kaarten staat ná de EER-guard. Guards worden van boven naar beneden getest, dus een zakelijke Visa uit de EER valt al op regel 14 in het consumententarief: €3,00 in plaats van €25,00 op €1.000 (nagespeeld). Zakelijke kaarten van buiten de EER en Amex kloppen wel, en daarom ziet een test met alleen die gevallen het niet. De compiler meldt niets: dominantie geldt alleen voor cases zonder guard. Zet de commercial-guard tussen de Amex- en de EER-regel, en vraag om een test per rij van de tarieftabel, inclusief de combinatie EER + zakelijk. Waarom major en geen blocker: het is een te lage fee die je kunt nafactureren, geen geld dat verdwijnt of een flow die stopt; maar het moet vóór de merge goed.

Regels 33–57 minor Speculatieve generaliteit: een interface, drie @Component-klassen en een factory voor één regel beleid: volledige refund gratis, gedeeltelijke €0,10. Er zijn twee gevallen, ze zijn uitputtend (volledig of niet) en geen van beide heeft dependencies. De lezer moet nu vier bestanden openen om refund.isFull() ? ZERO : new BigDecimal("0.10") te vinden. Voorstel: een private methode refundFee(Refund) in RefundService, of een regel in de bestaande tariefconfiguratie als Pricing hem wil kunnen wijzigen. Wordt de refund-fee ooit per contract of per methode verschillend, dan is dat data (een tarieftabel), geen nieuwe klasse per geval. Minor, geen nit: het blijft niet bij deze PR, want het volgende "geval" wordt nu een vijfde klasse.

Regels 23–31 geen probleem De afleider. Weer een switch op het type van de betaalmethode, de derde in deze PR: lijkt op "dezelfde switch op drie plekken". Maar het is een andere operatie (settlementvertraging, van Treasury), over een sealed type, zonder default. Dat is hoe variant E bedoeld is: dit is de switch die de compiler wél aanwees, en daarom staat PayByBank er correct in. Verplaatsen naar een methode settlementDelay() op het record zou Treasury-beleid in het domeintype trekken.

Regel 62 geen probleem Een losse instanceof PayByBank p is geen keten: alleen Pay by Bank heeft een providerconfig nodig, en alle andere types (ook toekomstige) doen hier niets. Een switch met case Card _, Ideal _, SepaDebit _ -> {} voegt alleen ruis toe. Het probleem op deze regels is orElse, niet de instanceof.

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 2 · voorspellen

    Team Payments voegt record PayByBank toe aan de sealed PaymentMethod in payment-model.jar en deployt. pricing.jar en reporting.jar worden niet opnieuw gebouwd. Daarin staan:

    pricing.jar

    return switch (method) {
    case Card c -> cardFee(c, amount);
    case Ideal _ -> IDEAL_FEE;
    case SepaDebit _ -> SEPA_FEE;
};

    reporting.jar

    String label = switch (method) {
    case Card _ -> "Kaart";
    case Ideal _ -> "iDEAL";
    default -> "SEPA-incasso";
};

    Wat gebeurt er in elk van de twee jars bij de eerste Pay-by-Bank-betaling?

    Antwoord tonen

    Pricing gooit MatchException; reporting labelt de betaling stil als "SEPA-incasso".

    Waarom

    • Bij een exhaustive switch zonder default zet de compiler zelf een tak neer die MatchException gooit als er tijdens runtime een onbekend type langskomt. Nagespeeld op JDK 25: java.lang.MatchException, zonder message.
    • Met default is er geen onbekend type: alles wat niet Card of Ideal is, is "SEPA-incasso". Geen fout, geen log, verkeerde rapportage.
    • Pricing faalt luid, en dat is de goede uitkomst. Had iemand pricing.jar tegen de nieuwe versie gebouwd, dan was het een compileerfout geweest; reporting had ook dan gecompileerd.

    In de review

    issue: de default in reporting labelt elk toekomstig type als SEPA-incasso. Zonder default wordt het een compileerfout bij de volgende betaalmethode. En zorg dat CI alle modules tegen de nieuwe payment-model bouwt, anders zie je het pas als MatchException in productie.

  2. Vraag 2Doel 2 · voorspellen

    Twee pogingen om zakelijke kaarten een eigen tarief te geven.

    A

    case Card c -> percent(amount, "1.90");
case Card c when c.commercial()
        -> percent(amount, "2.50");

    B

    case Card c when c.issuerRegion() == EEA
        -> percent(amount, "0.30");
case Card c when c.commercial()
        -> percent(amount, "2.50");
case Card _ -> percent(amount, "1.90");

    Welke compileert, en welk tarief krijgt een zakelijke kaart uit de EER in de variant die compileert?

    Antwoord tonen

    A compileert niet; B compileert en geeft de zakelijke EER-kaart 0,30%.

    Waarom

    • A: case Card c zonder guard vangt elke kaart, dus de regel eronder kan nooit worden bereikt. Fout: this case label is dominated by a preceding case label.
    • B: guards worden van boven naar beneden getest; de eerste die past wint. De compiler controleert niet of guards overlappen, en geeft ook met -Xlint:all geen waarschuwing.
    • De compiler vangt dus de onschuldige fout (A) en laat de gevaarlijke (B) door.

    Let op

    • Lees een switch met guards als een beslistabel en vraag per rij welke input die voor een lagere rij bedoeld is, hier al wordt gevangen. Vraag om een test voor elke combinatie die twee guards tegelijk waar maakt.
  3. Vraag 3Doel 1 · herkennen

    In LedgerService staat al jaren deze switch. De PR voegt PARTIALLY_REFUNDED toe aan enum PaymentStatus en is groen.

    switch (payment.status()) {
    case AUTHORISED -> ledger.reserve(payment);
    case CAPTURED -> ledger.book(payment);
    case REFUNDED -> ledger.reverse(payment);
}

    Waarom gaf de compiler geen fout, en wat stel je voor?

    Antwoord tonen

    Een switch-statement over een enum zonder patterns hoeft niet exhaustive te zijn; PARTIALLY_REFUNDED boekt stil niets.

    Waarom

    • JLS §14.11.2: alleen enhanced switch-statements (met patterns of case null, of met een selector die geen enum, String of int-achtig type is) moeten exhaustive zijn. Deze is dat niet, ook met pijlen. Nagespeeld: compileert, en de nieuwe constante doet niets.
    • Een switch-expressie over dezelfde enum had wel een fout gegeven, net als dit statement met een extra case null -> throw … (dat maakt hem enhanced; nagespeeld).

    In de review

    issue (blocking): deze switch-statement is niet exhaustive-gecontroleerd, dus PARTIALLY_REFUNDED komt nooit in het grootboek. Kun je hem omschrijven naar een expressie (bijv. een LedgerAction teruggeven) of een case null toevoegen? Dan wordt de volgende status een compileerfout. Wat moet PARTIALLY_REFUNDED boeken?

  4. Vraag 4Doel 3 · kiezen

    Een PR modelleert de externe fraudecheck-leveranciers (twee nu, naar verwachting elk kwartaal één erbij) als sealed interface RiskProvider met een record per leverancier, en een switch in RiskService die per record de juiste HTTP-client aanroept. Elke leverancier heeft eigen credentials, timeouts en foutcodes; de enige operatie is score(Payment).

    Keur je dit ontwerp goed, en met welk argument?

    Antwoord tonen

    Nee: hier groeien de types en staat de operatie vast. Dat is een interface met een bean per leverancier.

    Waarom

    • Met de sealed variant wordt elke nieuwe leverancier een wijziging in RiskService, die daardoor afhankelijk wordt van elke client. De exhaustiveness-controle beschermt één switch die er niet hoeft te zijn.
    • interface RiskProvider { ProviderId id(); RiskScore score(Payment p); } met een @Component per leverancier houdt elke client met zijn eigen config bij elkaar. Een nieuwe leverancier raakt geen bestaand bestand.
    • Vergelijk met PaymentMethod: weinig nieuwe types, veel operaties van verschillende teams. Daar wint de sealed switch.

    In de review

    suggestion: hier komen elk kwartaal leveranciers bij en blijft de operatie score. Een RiskProvider-interface met een bean per leverancier houdt elke client en zijn config bij elkaar, en een nieuwe leverancier wordt één nieuwe klasse in plaats van een wijziging in RiskService. Sealed + switch past beter waar de operaties groeien, zoals bij PaymentMethod.

  5. Vraag 5Doel 4 · zwaarte

    Een collega "verbetert" een switch over de sealed PaymentMethod die alle vier de subtypes afdekt:

            case PayByBank _ -> Period.ofDays(1);
+       default -> throw new IllegalStateException("Onbekende methode: " + method);
    };

    Welke zwaarte geef je, en wat schrijf je?

    Antwoord tonen

    minor: het faalt luid, maar het zet een compileerfout om in een runtime-fout.

    Waarom deze zwaarte

    • Vandaag verandert er niets: de switch is al exhaustive, en een overbodige default geeft geen fout of waarschuwing.
    • Bij het volgende subtype compileert deze switch gewoon door, en vind je hem pas als de exception in productie vliegt. Zonder de default was het een compileerfout geweest.
    • Het "vangnet" bestaat al: zonder default zet de compiler zelf een MatchException-tak neer voor het geval van aparte compilatie. Geen blocker, omdat er geen fout resultaat ontstaat (anders dan bij default -> Period.ofDays(2)).

    In de review

    suggestion: zou je deze default willen weghalen? De switch dekt alle subtypes al af, en met default wordt de volgende betaalmethode een runtime-exception in plaats van een compileerfout hier. Voor het geval dat een module niet opnieuw wordt gecompileerd, gooit Java zelf al een MatchException.
