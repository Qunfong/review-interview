Streams lezen en schrijven

Een stream ziet eruit als een rij bewerkingen, maar het is een luie pijplijn die zelf bepaalt wat hij wanneer en op welke thread uitvoert. Wie dat vergeet, schrijft een uitbetaalrun die in de test klopt en in productie per run een ander totaal oplevert, of die stopt zodra één merchant een tweede valuta aanzet.

Tijd 45 minStack Java 25 (gedrag gedraaid op JDK 17 en 25)

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Wat print List.of("a", "b", "c").stream().peek(System.out::println).count() op Java 17 of later?
  2. toMap(PayoutAccount::merchantId, Function.identity()) krijgt twee rekeningen van dezelfde merchant. Wat gebeurt er, en is een merge-functie (a, b) -> a de oplossing?
  3. Je vervangt .collect(Collectors.toList()) door .toList(). Welke aanroeper kan daardoor breken?

Wat er onder de motorkap gebeurt

Een stream is een beschrijving van werk, geen uitvoering. filter, map en peek bouwen alleen een pijplijn op. Pas de terminale stap (collect, toList, findFirst, count, forEach) trekt elementen door die pijplijn. Zonder terminale stap gebeurt er niets, ook geen peek.

Drie gevolgen die je in een review moet kunnen uitleggen:

  • Per element, niet per stap. Elk element gaat de hele keten door voordat het volgende begint. findFirst stopt zodra het een resultaat heeft; de rest van de bron wordt nooit gelezen. Een stateful stap als sorted() is een barrière: die moet eerst alles binnenhalen voordat hij iets kan doorgeven.
  • Stappen mogen worden overgeslagen. De java.util.stream-documentatie garandeert niet dat lambda's in tussenstappen worden aangeroepen. count() op een bron waarvan de grootte bekend is (een List zonder filter) slaat de hele pijplijn over, inclusief je peek. Alleen forEach en forEachOrdered voeren hun actie gegarandeerd uit.
  • Thread en volgorde zijn niet van jou. Bij parallelStream() draaien je lambda's tegelijk op de gedeelde ForkJoinPool.commonPool() en op de aanroepende thread. Een lambda die een gedeelde HashMap of ArrayList muteert, heeft dan een data race. Een collector heeft dat probleem niet: elke thread vult zijn eigen container, en een combiner voegt die daarna samen. Daarom is collect de veilige manier om een stream naar een resultaat te brengen, en forEach naar gedeelde state niet.

Geverifieerd: alle gedragsclaims in deze module zijn gedraaid op JDK 17.0.8 en JDK 25.0.4, met een trace in elke lambda. Paneel A: de trace is filter tx1, filter tx2, map tx2; met sorted() wordt het filter ×4, daarna één map. List.of(...).stream().peek(...).count() riep peek op beide versies nul keer aan; met een filter ervoor drie keer.

Uitgewerkt voorbeeld

De dagelijkse uitbetaalrun. Uit alle afgewikkelde transacties van gisteren berekent PayoutCalculator per merchant het saldo (captures min refunds en chargebacks) en koppelt dat aan een uitbetaalrekening. Het resultaat gaat als betaalbestand naar de bank. Er zijn zo'n 200.000 transacties per dag, en de auteur heeft parallelStream() gebruikt "omdat het veel data is".

De unit-test met tien transacties en één rekening per merchant is groen. Wat er in productie gebeurt:

  1. De totalen kloppen niet, en elke run anders. Meerdere threads roepen tegelijk HashMap.merge aan. In onze run (200.000 transacties, 500 merchants, 20 herhalingen) gaf ongeveer de helft van de runs een totaal dat tienduizenden euro's afweek, en de andere helft een ConcurrentModificationException. Geen enkele run was goed. Sequentieel klopt dezelfde code wel; daarom ziet de test het niet.
  2. De sleutel is fout. Een merchant met EUR- en USD-omzet krijgt één totaal: €100 capture + $50 capture − €20 refund = 130, uitbetaald op de EUR-rekening. Dit is een domeinfout, maar de stream verstopt hem: totals ziet eruit als "per merchant", en dat leest als correct.
  3. De dag dat een merchant een USD-rekening krijgt, stopt de hele run. toMap zonder merge-functie gooit bij een dubbele sleutel een IllegalStateException: Duplicate key MerchantId[value=m-42] (attempted merging values PayoutAccount[…] and PayoutAccount[…]). Niet alleen m-42, maar alle merchants worden die dag niet uitbetaald. Let ook op de melding zelf: daarin staan beide rekeningen via hun toString(), dus IBAN's in je errorlog.
  4. De verleidelijke fix maakt het erger. toMap(..., (a, b) -> a) laat de exception verdwijnen en kiest stil de eerste rekening. In onze run: de EUR-rekening, voor een bedrag waarin USD zit. De exception was het enige signaal dat de sleutel niet klopte.
  5. Kleinere punten: de volgorde van het betaalbestand verschilt per run (iteratievolgorde van een HashMap), en een merchant zonder rekening levert een Payout met null op, die pas ergens anders een NullPointerException geeft.

De herschrijving

Drie beslissingen, elk met een reden. De sleutel wordt (merchant, valuta), want dat is wat er werkelijk wordt uitbetaald. parallelStream() verdwijnt: 200.000 BigDecimal-optellingen in een nachtelijke batch zijn geen bottleneck, en wie het toch parallel wil, kan dat nu veilig doen omdat de collector per thread een eigen map vult (in onze run gaf de parallelle toMap exact hetzelfde resultaat). En de toMap zonder merge-functie op de rekeningen blijft bewust staan: twee rekeningen voor dezelfde merchant en valuta is een datafout die de run moet stoppen. Zet er wel een eigen exception omheen als de IBAN's niet in de log mogen.

Varianten voor de aggregatie, en hun prijs

De kern is "som per sleutel". Er zijn vier redelijke manieren om dat te schrijven. Alle vier gaven op dezelfde 200.000 transacties dezelfde map.

A · toMap met merge-functie

.collect(toMap(Transaction::payoutKey, Transaction::signedAmount, BigDecimal::add))

Kortst als er één waarde per sleutel uitkomt. De merge-functie ís de aggregatie. Prijs: wie toMap leest, verwacht een unieke sleutel; de derde parameter is makkelijk te missen. Kies deze vorm als de aggregatie een simpele BinaryOperator is.

B · groupingBy met downstream-collector

.collect(groupingBy(Transaction::payoutKey,
        reducing(BigDecimal.ZERO, Transaction::signedAmount, BigDecimal::add)))

Zegt "groeperen" in het eerste woord, en schaalt naar andere aggregaties: counting(), mapping(..., toSet()), teeing(...). Prijs: voor een simpele som wordt reducing met drie argumenten wollig. Gebruik groupingBy(key, TreeMap::new, downstream) als de volgorde ertoe doet; de standaardvariant geeft geen garantie over het maptype (in de praktijk een HashMap).

C · Een gewone loop met merge

var totals = new HashMap<PayoutKey, BigDecimal>();
for (var tx : transactions) {
    if (tx.status() != Status.SETTLED) continue;
    totals.merge(tx.payoutKey(), tx.signedAmount(), BigDecimal::add);
}

Even correct en voor veel lezers even helder. De mutatie is lokaal en ontsnapt niet. Prijs: niet parallelliseerbaar zonder herschrijving, en vier regels in plaats van drie. Een prima keuze zodra de loop méér moet doen: een vroege exit, een tweede accumulator, een checked exception.

Niet doen · summingDouble op bedragen

.collect(groupingBy(Transaction::payoutKey,
        summingDouble(tx -> tx.signedAmount().doubleValue())))

Het kortst van allemaal, en fout voor geld. double kan 0,10 niet exact opslaan. summingDouble gebruikt een gecompenseerde sommatie (tien keer 0,10 gaf netjes 1.0, waar een naïeve loop 0.9999999999999999 gaf), maar 0,10 + 0,20 gaf alsnog 0.30000000000000004. Bedragen blijven BigDecimal of long in centen.

Twee keuzes die je in bijna elke PR tegenkomt

Twee aggregaten in één keer. Captured en refunded totaal over dezelfde transacties. Met teeing in één pass:

teeing

.collect(teeing(
    filtering(tx -> tx.type() == CAPTURE,
        reducing(ZERO, Transaction::amount, BigDecimal::add)),
    filtering(tx -> tx.type() != CAPTURE,
        reducing(ZERO, Transaction::amount, BigDecimal::add)),
    Settlement::new));

loop met twee accumulatoren

var captured = ZERO;
var refunded = ZERO;
for (var tx : settled) {
    if (tx.type() == CAPTURE) captured = captured.add(tx.amount());
    else refunded = refunded.add(tx.amount());
}
return new Settlement(captured, refunded);

Beide geven hetzelfde. Hier wint de loop: één if in plaats van twee filtering-predicaten die elkaars complement moeten zijn (een vierde Type erbij en je moet in de teeing-variant twee plekken bijwerken). teeing verdient zijn plek als downstream binnen een groupingBy, waar je geen lokale variabelen hebt; zie de oefening.

Welke toList? De IDE stelt voor om collect(Collectors.toList()) te vervangen door toList(). Dat is geen gedragsneutrale refactoring:

Zelfde soort valkuil: sorted(c).findFirst() waar min(c) volstaat. Het resultaat is gelijk, ook bij gelijke waarden (beide geven het eerste element in de bronvolgorde; nagespeeld), maar sorted kopieert en sorteert alles in O(n log n) om één element te vinden, en zegt minder duidelijk wat je bedoelt.

Wanneer het géén probleem is

  • Een loop in plaats van een stream als de logica een vroege return of break heeft, meerdere accumulatoren bijhoudt, een checked exception doorgeeft of met indexen of het vorige element werkt. Een stream die daarvoor een AtomicInteger, een array-truc of een try/catch in een lambda nodig heeft, is slechter, niet moderner. "Maak hier een stream van" zonder concreet leesvoordeel is geen comment waard.
  • Een sequentiële forEach die een lokale map vult. Die is correct (nagespeeld: sequentieel klopt het totaal). Het is een loop in vermomming en een collector zegt het beter, maar dat is hooguit een nit. Het wordt pas een probleem als de map gedeeld is of de stream parallel.
  • peek voor debug-logging. Daar is hij voor bedoeld, volgens de Javadoc zelf. Het probleem begint als iets ervan afhangt: een teller, een auditregel, een statuswijziging.
  • toMap zonder merge-functie als een dubbele sleutel echt een datafout is. Dan is de exception gewenst gedrag. Vraag alleen of het falen van de hele run de bedoeling is, en of de melding geen gevoelige data bevat.
  • Een geneste stream over een kleine, begrensde collectie (de vijf valuta's van een merchant). O(n·m) met m ≤ 5 is O(n).
  • parallel() op een grote, goed splitsbare bron (een ArrayList of array), met CPU-werk, zonder gedeelde state en buiten het request-pad, nadat iemand heeft gemeten dat het helpt.

Zwaarte: blocker als het resultaat fout of niet-deterministisch is (gedeelde mutable state in een parallelle stream, geld als double in een uitbetaling, een side effect waar compliance op rekent dat niet draait) of als realistische data de hele run laat falen · major bij O(n·m) op data die groeit, of een toList()-wissel terwijl een aanroeper de lijst wijzigt · minor of nit bij leesbaarheid: forEach naar een lokale map, sorted().findFirst(), een collector die een loop had moeten zijn · laat gaan bij stream-of-loop-voorkeur zonder concreet argument.

Zo schrijf je het op

Zwak

Geen forEach met side effects in een stream gebruiken, dat is niet functioneel. Graag een collector.

Klinkt als een stijlregel. Geen gevolg, geen bewijs, en de echte fout (de sleutel) blijft liggen. De auteur maakt er een collector van met (a, b) -> a en alles is erger.

Sterk

issue (blocking) forEach op een parallelStream() schrijft vanuit meerdere threads in één HashMap. Bij 200k transacties krijg je per run een ander totaal of een ConcurrentModificationException (lokaal nagespeeld: geen enkele run van 20 klopte). De test met 10 transacties ziet dat niet.

Daarnaast: de sleutel is alleen de merchant, dus EUR en USD worden bij elkaar opgeteld. De toMap op de rekeningen gooit zodra een merchant twee rekeningen heeft, en dan stopt de run voor iedereen.

Voorstel: .stream().collect(toMap(Transaction::payoutKey, Transaction::signedAmount, BigDecimal::add)) met PayoutKey(merchant, currency), en de rekeningen ook op PayoutKey. Is parallel gemeten? Zo niet, laat hem weg.

Antwoordsleutel tonen

Regels 30–32 blocker De auditregels worden nooit geschreven. cbs is een List, er staat geen filter tussen, dus count() kan het antwoord uit de grootte van de bron halen en slaat de pijplijn over, inclusief peek. Nagespeeld op JDK 17 en 25: audited is 3, het aantal auditregels 0. Het rapport beweert dus dat alles geaudit is, terwijl het compliance-log leeg blijft. Het gedrag is ook fragiel: zet iemand er later een filter tussen, dan draait peek ineens wel. Herschrijving: maak de side effect expliciet met cbs.forEach(auditTrail::recordIncluded) en gebruik cbs.size() voor het aantal. forEach is de enige plek waar een side effect gegarandeerd draait, en de lezer ziet meteen dat hier iets gebeurt.

Regels 24–25 major Per merchant twee keer door alle chargebacks lopen: 30.000 × 40.000 × 2 = 2,4 miljard equals-aanroepen per rapport, en dat groeit kwadratisch mee met het volume. Herschrijving: groepeer één keer, met beide aggregaten tegelijk. Hier past teeing wél, als downstream van groupingBy:

Lineair, één pass over de chargebacks, en de filter op regel 27 wordt overbodig, omdat alleen merchants met chargebacks in stats staan. (ReportRow krijgt daarvoor een ChargebackStats-component in plaats van de losse long en double.) De lezer ziet nu "groepeer per merchant, tel en tel op" in plaats van een geneste stream die hij in zijn hoofd moet uitvoeren. Deze code is gecompileerd en gedraaid.

Regels 26 en 58 major Bedragen als double. Nagespeeld: twee chargebacks van 0,10 en 0,20 geven chargebackAmount = 0.30000000000000004. In een CSV voor risk is dat een afwijking van een fractie van een cent, maar het type ReportRow.chargebackAmount is een API: de volgende die het optelt voor een boekingsregel erft de fout. Gebruik BigDecimal met reducing (zie hierboven). Waarom major en geen blocker: dit rapport betaalt niets uit; in een uitbetaling was het een blocker geweest.

Regels 14 en 39 minor Uit module 1 (transacties). De SFTP-upload draait binnen de readOnly-transactie, dus er staat 2–20 s een databaseconnectie vast terwijl er niets met de database gebeurt. Omdat het rapport één keer per dag draait, is het risico op een lege pool klein; daarom minor, geen blocker. Maar de transactie heeft geen functie na regel 18. Voorstel: haal de data op in een transactionele methode (of zonder transactie: het zijn drie losse reads), en upload daarbuiten. Wordt generate later ook via een endpoint aangeroepen, dan wordt dit major.

Regels 34–37 nit sorted(...reversed()).findFirst() is max(comparingDouble(ReportRow::ratio)). Waarom de herschrijving beter is: hij zegt wat je zoekt ("de grootste") in plaats van hoe je hem vindt, is O(n) in plaats van O(n log n) zonder kopie van de hele lijst, en geeft bij gelijke ratio's hetzelfde element terug (nagespeeld). Laat daarbij orElse(null) los en geef de Optional door aan ReportSummary; een null in een record verschuift de check naar elke lezer.

Regels 43–53 geen probleem De afleider: een gewone for-loop met continue en vroege return. De stream-variant (filter(...).filter(...).findFirst()) is even kort en geeft hetzelfde resultaat (nagespeeld), maar is niet beter. De loop laat de vroege exit en de reden voor het overslaan net zo duidelijk zien. Een comment "maak hier een stream van" kost de auteur tijd en jou geloofwaardigheid.

Regel 28 geen probleem .toList() levert een onwijzigbare lijst op, en dat is hier precies goed: rows wordt daarna alleen gelezen (stream, CSV, size()).

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 1 · beoordelen

    Twee versies van het inlezen van een betaalbestand. PayoutInstruction.parse gooit de checked InvalidIbanException met het regelnummer erin.

    A · loop

    List<PayoutInstruction> parse(List<String> lines)
        throws InvalidIbanException {
    var result = new ArrayList<PayoutInstruction>();
    for (int i = 0; i < lines.size(); i++) {
        result.add(PayoutInstruction.parse(lines.get(i), i + 1));
    }
    return result;
}

    B · stream

    List<PayoutInstruction> parse(List<String> lines) {
    return IntStream.range(0, lines.size())
            .mapToObj(i -> {
                try {
                    return PayoutInstruction.parse(lines.get(i), i + 1);
                } catch (InvalidIbanException e) {
                    throw new RuntimeException(e);
                }
            })
            .toList();
}

    Welke versie keur je goed, en met welk argument?

    Antwoord tonen

    A. De stream voegt hier niets toe en kost een contract.

    Waarom

    • B moet de checked exception inpakken in een generieke RuntimeException. De aanroeper ziet niet meer dat een ongeldige IBAN een verwacht geval is, en een catch (InvalidIbanException e) hogerop vangt niets meer.
    • Het regelnummer maakt het indexlogica. IntStream.range plus lines.get(i) is een loop in vermomming.
    • Let op het gedragsverschil: A geeft een wijzigbare lijst terug, B een onwijzigbare. Een aanroeper die sorteert, breekt bij de "opschoning" van A naar B.

    In de review

    suggestion: hier zou ik de loop houden. De stream dwingt een try/catch in de lambda af die InvalidIbanException in een RuntimeException verpakt, waardoor de aanroeper het checked contract kwijtraakt. Met het regelnummer erbij is de loop ook gewoon leesbaarder.

  2. Vraag 2Doel 2 · herkennen en herschrijven

    Een batch zoekt de orders die opnieuw aangeboden moeten worden:

    List<OrderId> retry = new ArrayList<>();
orders.parallelStream()
      .filter(Order::needsRetry)
      .forEach(o -> retry.add(o.id()));
retryQueue.submitAll(retry);

    Wat gaat hier mis, en hoe herschrijf je het?

    Antwoord tonen

    Meerdere threads doen tegelijk add op een ArrayList; herschrijf naar .map(Order::id).toList().

    Waarom

    • ArrayList is niet thread-safe. Nagespeeld met 100.000 orders en 20 runs: de meeste runs eindigden in een ArrayIndexOutOfBoundsException, de rest gaf een lijst met de verkeerde grootte of met null-elementen. Orders vallen dus stil buiten de retry.
    • toList() is een collector-achtige terminale stap: elke thread bouwt een eigen deel en die worden samengevoegd. Het resultaat had de goede grootte en stond zelfs in bronvolgorde, ook parallel.

    Let op

    • Een Collections.synchronizedList om retry heen "werkt" ook, maar maakt van de parallelle stream een wachtrij voor één lock en laat de volgorde willekeurig. De vraag is eerder of parallel hier iets oplevert.
  3. Vraag 3Doel 3 · kiezen

    Refunds boven een limiet hebben een tweede paar ogen nodig:

    Map<Boolean, List<Refund>> split = refunds.stream()
        .collect(groupingBy(r -> r.amount().compareTo(FOUR_EYES_LIMIT) > 0));
split.get(true).forEach(fourEyes::request);
split.get(false).forEach(refundExecutor::execute);

    Wat gebeurt er op een dag zonder grote refunds, en welke collector hoort hier?

    Antwoord tonen

    Een NullPointerException op split.get(true); gebruik partitioningBy.

    Waarom

    • groupingBy maakt alleen sleutels aan voor waarden die voorkomen. Zonder grote refunds bestaat true niet (nagespeeld: get(true) is null).
    • partitioningBy garandeert volgens de Javadoc altijd beide sleutels, met een lege lijst als er niets in valt.
    • Erger dan de NPE: de normale refunds op de regel erna worden die dag ook niet uitgevoerd.

    In de review

    issue: groupingBy op een boolean levert geen true-sleutel op als er geen enkele refund boven de limiet zit, en dan gooit regel 3 een NPE en draaien de normale refunds ook niet. partitioningBy heeft altijd beide sleutels.

  4. Vraag 4Doel 3 · verdedigen

    Een opschoon-PR vervangt op 140 plekken .collect(Collectors.toList()) door .toList(), met als toelichting: "IntelliJ-inspectie, puur cosmetisch."

    Wat controleer je voordat je deze PR goedkeurt?

    Antwoord tonen

    Of een aanroeper de teruggegeven lijst wijzigt, want toList() is onwijzigbaar.

    Waarom

    • Collectors.toList() geeft in de praktijk een ArrayList. Code die daarna add, remove of sort doet, werkt nu en gooit straks een UnsupportedOperationException (nagespeeld voor add en sort). Dat kan drie lagen verderop gebeuren, in een andere klasse.
    • null-elementen zijn geen probleem: Stream.toList() laat ze toe, net als Collectors.toList(). toUnmodifiableList() zou wel met een NPE falen.
    • De wijziging is op zich een verbetering: onwijzigbaar is het betere standaardgedrag. Alleen "puur cosmetisch" klopt niet.

    In de review

    question: toList() is onwijzigbaar, Collectors.toList() in de praktijk niet. Heb je gecontroleerd dat geen van de 140 resultaten later wordt aangepast of gesorteerd? Anders liever in kleinere stappen, met tests rond de plekken waar de lijst de methode verlaat.

  5. Vraag 5Doel 4 · zwaarte en comment

    In een REST-controller, met de toelichting "parallel maakt het 8× sneller":

    @GetMapping("/orders/status")
List<PaymentStatus> statuses(@RequestParam List<UUID> orderIds) {
    return orderIds.parallelStream()
            .map(pspClient::fetchStatus)    // HTTP-call naar de PSP, 100–800 ms
            .toList();
}

    Welke zwaarte geef je, en wat schrijf je?

    Antwoord tonen

    major: blokkerende I/O op de gedeelde common pool, in het request-pad.

    Waarom deze zwaarte

    • Parallelle streams draaien op ForkJoinPool.commonPool() plus de aanroepende thread (nagespeeld: de threads heetten ForkJoinPool.commonPool-worker-N en main). Die pool is gedeeld door de hele JVM en heeft standaard aantal cores − 1 threads (7 op een machine met 8).
    • Tien gelijktijdige requests met elk 50 ID's houden die paar threads honderden milliseconden bezet met wachten op HTTP. Elke andere parallelle stream in de applicatie staat dan stil.
    • De "8×" hangt af van het aantal cores, niet van wat de PSP aankan. Er is geen grens op het aantal gelijktijdige calls per request en geen timeout. Geen blocker, omdat er geen data misgaat, maar wel iets dat onder belasting omvalt.

    In de review

    issue: parallelStream() met een HTTP-call per element draait op de gedeelde common pool (cores − 1 threads). Onder belasting blokkeren deze calls alle andere parallelle streams in de JVM, en het aantal gelijktijdige PSP-calls is niet begrensd. Voorstel: een virtual-thread-executor met een Semaphore als grens, of Gatherers.mapConcurrent (Java 24+, zie F5). Plus een timeout op de client.
