Transacties en proxies

@Transactional is geen taalconstructie maar een proxy die om je bean heen zit. Wie dat vergeet, schrijft code die in de test groen is en in productie een terugbetaling uitvoert zonder dat de database het weet.

Tijd 40 minStack Java 25 · Spring Boot 4 (Framework 7)

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. Een @Transactional-methode roept this.audit() aan, en audit() heeft REQUIRES_NEW. Hoeveel transacties zijn er?
  2. Een @Transactional-methode gooit een IOException. Wordt er teruggerold?
  3. Je vangt binnen een transactie een exception uit een andere @Transactional-bean en gaat door. Wat gebeurt er bij de commit?

Wat er onder de motorkap gebeurt

Spring Boot geeft je niet je eigen PaymentService, maar een subklasse die CGLIB tijdens het opstarten genereert (Boot zet spring.aop.proxy-target-class standaard op true). Die proxy overschrijft elke methode waar een transactie-attribuut op zit en stuurt de aanroep door de TransactionInterceptor: transactie openen of meedoen, de echte methode aanroepen op het doelobject, daarna commit of rollback.

Het doelobject zelf weet niets van transacties. Binnen het doelobject is this het doelobject, niet de proxy. Een aanroep this.recordDecline() is dus een gewone Java-methodeaanroep: geen interceptor, geen REQUIRES_NEW, geen rollbackFor, geen timeout. De annotatie staat er, maar niemand leest hem.

Daaruit volgen ook de andere gevallen:

  • private: een subklasse kan een private methode niet overschrijven, dus de proxy kan er niet tussen. Nooit transactioneel met proxy-AOP.
  • protected en package-private: sinds Spring Framework 6.0 wel transactioneel bij CGLIB-proxies, als ze via de proxy worden aangeroepen. De oude regel "alleen public" klopt niet meer. Bij JDK-interfaceproxies telt alleen wat in de interface staat.
  • final: de proxy kan de methode niet overschrijven, dus de aanroep draait op de proxy-instantie zelf. Die is zonder constructor aangemaakt; haar velden zijn null. Resultaat: een NullPointerException op je repository, of, als de methode geen velden gebruikt, stil geen transactie. Spring logt bij het opstarten een WARN: cannot get proxied via CGLIB.

Propagation bepaalt wat de interceptor doet als er al een transactie loopt. REQUIRED (standaard) doet mee in de bestaande transactie. REQUIRES_NEW schorst de bestaande transactie en opent een nieuwe, op een tweede databaseconnectie, terwijl de eerste vast blijft.

Geverifieerd: alle gedragsclaims in deze module zijn nagespeeld met Spring Framework 7.0.9, DataSourceTransactionManager en H2. In pad A meldt TransactionSynchronizationManager.getCurrentTransactionName() binnen writeAudit() de naam van de buitenste methode; na de rollback staan er 0 auditregels. In pad B blijft de regel staan.

Uitgewerkt voorbeeld

Een kaartautorisatie. Bij onvoldoende saldo wordt de autorisatie geweigerd. De fraudeafdeling wil elke weigering vastleggen, want hun velocity-regel ("meer dan 5 weigeringen per kaart per 10 minuten: blokkeren") vangt card testing: iemand die met gestolen kaartnummers kleine bedragen probeert. De weigering moet dus blijven staan, ook als de autorisatie zelf terugrolt. De developer weet dat en zet REQUIRES_NEW op de methode die de weigering opslaat.

CardAuthorizationService.java

Stap voor stap, bij een kaart met €3 saldo en een poging van €5:

  1. De controller roept authorize aan via de proxy. De interceptor opent tx1.
  2. recordDecline(...) is this.recordDecline(...). Geen proxy, dus de REQUIRES_NEW-annotatie wordt niet gelezen. declines.save doet mee in tx1.
  3. AuthorizationDeclinedException is een RuntimeException. De interceptor rolt tx1 terug, inclusief de weigering.
  4. De velocity-regel ziet nul weigeringen. Een aanvaller kan onbeperkt kaartnummers proberen.

De unit-test met een gemockte DeclineRepository is groen: verify(declines).save(any()) klopt, want de methode wordt aangeroepen. Alleen een test tegen een echte database met een echte transactie laat zien dat de regel verdwijnt.

Oplossingen en hun prijs

A · Weigering is een uitkomst, geen exception

Geef Authorization.declined(...) terug en sla de weigering op in dezelfde transactie, die nu gewoon commit. Eén transactie, één connectie, geen propagation-trucs. Prijs: het contract verandert; callers die op de exception reageerden (bijv. een @ExceptionHandler die een 402 met ProblemDetail teruggeeft) moeten mee. Vaak de beste keuze: een geweigerde betaling is normaal bedrijfsgedrag.

B · Aparte bean met REQUIRES_NEW

Verplaats recordDecline naar een DeclineLog-bean en injecteer die. De aanroep gaat nu door een proxy. Prijs: per weigering twee connecties tegelijk vast. Bij een pool van 10 en 10 gelijktijdige weigeringen wacht elke thread op een tweede connectie die niet vrijkomt: pool-locking tot de connectionTimeout van HikariCP (standaard 30 s) verloopt.

C · TransactionTemplate met PROPAGATION_REQUIRES_NEW

Programmatic: in de constructor requiresNew = new TransactionTemplate(txManager) met setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW), en dan requiresNew.executeWithoutResult(s -> declines.save(...)). De transactiegrens staat zichtbaar in de code, geen extra bean. Prijs: dezelfde tweede connectie als B, en transactiecode tussen je domeinlogica.

Wanneer het géén probleem is

  • Aanroep via this naar een methode zonder eigen annotatie. Die draait gewoon in de transactie van de aanroeper, en dat is precies wat je wilt. Private helpers als validate() of toResponse() zijn prima.
  • Aanroep via this naar een @Transactional-methode met dezelfde attributen (beide REQUIRED, geen readOnly, timeout of rollbackFor die afwijkt). Het gedrag is identiek; de annotatie is alleen misleidend. Hoogstens een nit.
  • @Transactional op class-niveau in een eenvoudige CRUD-service: elke publieke methode één transactie, zonder remote calls. Saai en correct.
  • Checked exception die níét terugrolt kan bedoeld zijn: de bestelling is opgeslagen, alleen de bevestigingsmail faalde. Vraag het, ga er niet vanuit dat het fout is. Wil een team dat elke exception terugrolt, dan kan dat sinds Spring 6.2 globaal met @EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS).
  • REQUIRES_NEW met een lage aanroepfrequentie (een nachtelijke batch, een admin-actie) maakt het pool-locking-risico verwaarloosbaar.

Zwaarte: blocker als er data verdwijnt of blijft staan die geld, compliance of fraudedetectie raakt, of als een remote side-effect (betaling, refund) buiten de transactie al gebeurd is · major als een attribuut stil genegeerd wordt (readOnly, timeout, rollbackFor) zonder dat er nu data misgaat · nit als de annotatie alleen overbodig is · laat gaan bij self-calls naar methoden zonder annotatie.

Zo schrijf je het op

Zwak

Self-invocation werkt niet met @Transactional. Graag fixen.

Geen gevolg, geen voorstel. De auteur weet niet waarom het ertoe doet en kan het wegwuiven als theorie.

Sterk

issue (blocking) recordDecline wordt via this aangeroepen, dus de Spring-proxy wordt overgeslagen en REQUIRES_NEW doet niets. De weigering zit in dezelfde transactie als authorize en rolt terug door de AuthorizationDeclinedException.

Gevolg: de velocity-regel telt geen weigeringen, dus card testing wordt niet geblokkeerd.

Voorstel: geef een declined-resultaat terug in plaats van te gooien (één transactie), of verplaats het opslaan naar een eigen DeclineLog-bean. Een integratietest die na een weigering het aantal declines in de DB telt, vangt dit.

Antwoordsleutel tonen

Regels 31–35 (met 63–66) blocker De catch redt niets. revokePoints loopt via de proxy van LoyaltyService en doet mee in de transactie van refund (REQUIRED). Klant zonder loyaltyaccount: LoyaltyAccountNotFoundException, de interceptor markeert de gedeelde transactie als rollback-only. De exception wordt gevangen, refund keert normaal terug, en de commit gooit UnexpectedRollbackException. Refund-regel en refundedAmount zijn weg, maar de PSP heeft het geld al teruggestort (regel 28). De client krijgt een 500 en probeert het opnieuw: dubbele refund. Voorstel: punten intrekken na de commit, via @TransactionalEventListener(phase = AFTER_COMMIT) of een outbox (module 3), of minimaal REQUIRES_NEW op revokePoints.

Regel 28 blocker Remote call binnen de transactie. Twee gevolgen. (1) Een databaseconnectie staat 200–2000 ms vast terwijl er niets met de database gebeurt; bij piekbelasting raakt de pool leeg en lopen ook ongerelateerde endpoints vast. (2) Belangrijker: als de commit daarna faalt (zie hierboven, of een constraint, of een deadlock), is het geld wel terug bij de klant maar weet de database het niet. Voorstel: splits in drie stappen. Transactie 1 legt de refund vast als REQUESTED; daarna de PSP-call buiten een transactie, met een idempotency key (het refund-id); transactie 2 zet hem op CONFIRMED.

Regels 20 en 28 major PspUnavailableException is checked, en checked exceptions rollen standaard niet terug. Is de PSP onbereikbaar, dan commit de transactie: er staat een refund op REQUESTED en refundedAmount is verhoogd, terwijl er geen geld is teruggestort. Het resterende bedrag klopt niet meer; bij een volledige refund wordt een tweede poging op regel 44 zelfs geweigerd. Voorstel: rollbackFor = PspUnavailableException.class, of (beter, met de opsplitsing hierboven) refundedAmount pas ophogen bij CONFIRMED.

Regel 47 major Uit het domein Correctheid. BigDecimal.equals vergelijkt ook de schaal: 100.0 en 100.00 zijn niet gelijk. Komt het bedrag als 100.0 binnen en staat het in de DB als 100.00, dan omzeilt een volledige refund tijdens een lopend dispuut deze check. Gebruik compareTo(...) == 0, zoals regel 44 wel doet.

Regel 23 / 39 geen probleem De afleider: een aanroep via this naar een private methode. Die heeft geen eigen transactie-annotatie en hoeft die ook niet: hij draait gewoon binnen de transactie van refund, en zijn RefundNotAllowedException (unchecked) rolt die terug voordat er iets is opgeslagen. Hier een comment over self-invocation plaatsen kost je geloofwaardigheid.

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 1 · herkennen

    Een collega maakt authorize final, "omdat niemand hem mag overschrijven":

    @Transactional
public final Authorization authorize(AuthorizeCommand cmd) {
    var card = cards.findByToken(cmd.cardToken())
            .orElseThrow(...);
    ...
}

    Wat gebeurt er bij de eerste request?

    Antwoord tonen

    Een NullPointerException op cards, en er is geen transactie.

    Waarom

    • CGLIB kan een final methode niet overschrijven, dus de aanroep loopt niet door de interceptor maar draait direct op de proxy-instantie.
    • Die proxy-instantie is zonder constructor aangemaakt: al haar velden, ook cards, zijn null.
    • Gebruikt de methode geen velden, dan gaat het stiller mis: hij draait gewoon, alleen zonder transactie.

    Waar je het ziet

    • Spring logt bij het opstarten een WARN dat de final methode niet geproxied kan worden. Zoek daarnaar in de log van de PR-build.
  2. Vraag 2Doel 2 · voorspellen

    Twee varianten van dezelfde @Transactional-methode. In beide gooit x() een IllegalStateException, en x() heeft zelf ook @Transactional.

    A · x() in dezelfde klasse

    try {
    x();            // this.x()
} catch (IllegalStateException e) {
    log.warn("x faalde", e);
}

    B · x() in een andere bean

    try {
    other.x();      // via proxy
} catch (IllegalStateException e) {
    log.warn("x faalde", e);
}

    Wat wordt er in A en in B gecommit?

    Antwoord tonen

    A commit gewoon. B gooit bij de commit een UnexpectedRollbackException en rolt alles terug.

    Waarom

    • A: de aanroep gaat via this, dus de interceptor ziet de exception nooit. Er wordt niets gemarkeerd, en jouw catch handelt hem af.
    • B: de interceptor van de andere bean ziet de exception en markeert de gedeelde transactie als rollback-only, nog vóórdat jouw catch hem vangt. De buitenste methode probeert te committen en krijgt de exception.

    Let op

    • De "kapotte" variant A doet hier toevallig wat de auteur bedoelde. Refactor je A naar een aparte bean, dan verandert het gedrag ongemerkt.
  3. Vraag 3Doel 3 · kiezen en verdedigen

    Fix B uit het voorbeeld (een aparte DeclineLog-bean met REQUIRES_NEW) gaat live. De connection pool heeft 10 connecties, de standaard van Spring Boot. Tijdens een card-testing-aanval komen er 50 weigeringen per seconde binnen.

    Wat zie je in productie, en welke fix had dit voorkomen?

    Antwoord tonen

    De pool loopt vast: na 30 seconden falen requests met SQLTransientConnectionException, ook ongerelateerde. Fix A had dit voorkomen.

    Waarom

    • Elke weigering houdt één connectie vast voor tx1 en vraagt er een tweede voor tx2.
    • Zodra alle 10 connecties als eerste connectie zijn uitgegeven, wacht iedereen op een tweede die nooit vrijkomt (pool-locking).
    • Na de connectionTimeout van HikariCP (standaard 30 s) volgen er exceptions. Je fraudelog faalt dus precies tijdens de aanval.

    De betere keuze

    • Fix A, de weigering als uitkomst in één transactie, heeft maar één connectie nodig. Blijf je bij B, dan moet de pool groter zijn dan het aantal threads dat tegelijk REQUIRES_NEW kan raken.
  4. Vraag 4Doel 2 · voorspellen

    Een PR zet @Transactional(readOnly = true) op ReportService, met als toelichting: "zo kan deze service nooit per ongeluk schrijven."

    Klopt die toelichting?

    Antwoord tonen

    Nee. readOnly is een hint voor performance, geen beveiliging.

    Waarom

    • Met JPA zet Spring de Hibernate-sessie op flush-mode MANUAL en read-only. Gewijzigde entities worden dus niet weggeschreven.
    • Een expliciete INSERT of UPDATE gaat wél naar de database. Of die daar geweigerd wordt, hangt af van driver en database. In onze test met H2 ging een INSERT gewoon door.
    • En net als elk transactie-attribuut werkt het alleen als de aanroep via de proxy loopt.

    In de review

    question: readOnly is een goede performance-hint, maar houdt een schrijfactie niet tegen. Is de bedoeling echt dat deze service nooit schrijft? Dan is een read-only databasegebruiker of een aparte read-only datasource de echte garantie.

  5. Vraag 5Doel 4 · zwaarte en comment

    De auteur schrijft erbij: "de timeout beschermt ons tegen een lock die blijft hangen."

    @Transactional
public void ship(Order order) {
    ...
    this.updateStatus(order);
}

@Transactional(timeout = 5)
public void updateStatus(Order order) { ... }

    Welke zwaarte geef je, en wat schrijf je in de review?

    Antwoord tonen

    major: de bescherming waar de auteur op rekent, bestaat niet.

    Waarom deze zwaarte

    • Via this wordt de proxy overgeslagen, dus timeout = 5 wordt nooit toegepast.
    • Er gaat nu geen data mis, dus geen blocker. Maar een hangende lock houdt de connectie zonder grens vast, en de auteur denkt dat dat is afgedekt.
    • Hadden beide methoden dezelfde attributen gehad, dan was het hooguit een nit.

    In de review

    issue: updateStatus wordt via this aangeroepen, dus de Spring-proxy wordt overgeslagen en timeout = 5 wordt genegeerd. Als de timeout belangrijk is: zet hem op ship, of verplaats updateStatus naar een eigen bean.
