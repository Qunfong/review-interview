Optional en afwezigheid

Eén woord verschil, orElse in plaats van orElseGet, en elke terugkerende klant krijgt bij de checkout een nieuw klantaccount bij de betaalprovider. Optional maakt afwezigheid zichtbaar, maar is gewone Java: argumenten worden eerst uitgerekend, en een verkeerd gekozen methode verstopt kosten, side effects of een NullPointerException.

Tijd 45 minStack Java 25 · Spring Boot 4 (Framework 7) · JSpecify 1.0

Na deze module kun je

Eerst zelf: beantwoord deze drie vragen in je hoofd voordat je verder leest.

  1. customers.findById(id).orElse(createDefault()): in welke gevallen draait createDefault()?
  2. Wat geeft Optional.of(order).map(Order::getVoucher) als getVoucher() null teruggeeft: een NPE, Optional[null] of iets anders?
  3. Je zet @Nullable van JSpecify op een parameter en compileert met gewone javac. Wat controleert de compiler nu?

Wat er onder de motorkap gebeurt

Optional is geen taalconstructie maar een gewone final klasse met een veld value dat wel of niet null is. Alles wat je ermee doet, volgt de normale regels van Java. De belangrijkste: Java rekent argumenten uit vóórdat de methode wordt aangeroepen (strict evaluation). Daaruit volgt bijna elke valkuil in deze module.

  • orElse(T other) krijgt een waarde. Staat er orElse(registerCustomer(cmd)), dan draait registerCustomer altijd, ook als de Optional gevuld is. Het resultaat wordt dan weggegooid; de side effects (HTTP-call, INSERT, bericht) niet.
  • orElseGet(Supplier), or(Supplier) en orElseThrow(Supplier) krijgen een functie. Die wordt alleen aangeroepen als de Optional leeg is.
  • map(f) pakt het resultaat in met ofNullable: geeft f null terug, dan krijg je Optional.empty(), geen exception. Daarom kun je een keten van getters die null kunnen geven veilig met map aflopen.
  • flatMap(f) verwacht dat f zelf een Optional teruggeeft. Geeft f null terug, dan volgt een NPE. Hetzelfde geldt voor een or-supplier die null teruggeeft.
  • Optional.of(x) gooit direct een NPE als x null is. Het is een bewering ("dit is nooit null"), geen conversie. ofNullable is de conversie.
  • orElseThrow() zonder argument en get() gooien allebei NoSuchElementException: No value present. De Javadoc noemt orElseThrow() de voorkeursvorm; get() is niet deprecated, maar de naam suggereert dat het altijd goed gaat.

Twee manieren om afwezigheid te typeren

Een senior reviewer ziet Optional niet als vervanging van null, maar als één van twee gereedschappen. De Javadoc van Optional is daar duidelijk over: bedoeld als "method return type where there is a clear need to represent 'no result'".

Optional<T>: een object

Bestaat tijdens runtime. Dwingt de aanroeper om iets met afwezigheid te doen, zonder tooling. Prijs: een extra object per aanroep, niet Serializable (een veld van dit type breekt Java-serialisatie), geen JPA-attribuuttype, en een Optional-variabele kan zelf nog steeds null zijn. Past bij: publieke returntypes van finders en lookups.

JSpecify @Nullable: een type-annotatie

org.jspecify.annotations.Nullable, met @NullMarked in package-info.java zodat alles zonder annotatie non-null is. Spring Framework 7 doet precies dat in zijn eigen packages; org.springframework.lang.Nullable is sinds 7.0 deprecated. Geen runtimekosten, maar gewone javac controleert niets: je hebt NullAway (in de build) of de IDE nodig. Past bij: velden, parameters, record-componenten, private methoden.

Twee details die je in een Spring 7-review tegenkomt:

  • Plaatsing. @Nullable is een TYPE_USE-annotatie en hoort direct vóór het type: private @Nullable Instant settledAt. Bij een volledig gekwalificeerd type moet hij ná de laatste punt: java.time.@Nullable Instant. @Nullable java.time.Instant compileert niet.
  • Spring Data 4 handhaaft het tijdens runtime. Staat een repository-interface in een @NullMarked package, dan gooit een finder met returntype PspCustomer (zonder @Nullable) een EmptyResultDataAccessException als er niets gevonden wordt, en een null-argument geeft een IllegalArgumentException. Met @Nullable PspCustomer krijg je null, met Optional<PspCustomer> een lege Optional. Het returntype is dus een contract dat het framework afdwingt.

Geverifieerd: het gedrag van Optional in deze module is nagespeeld met JDK 25.0.4 (Temurin): orElse roept het argument ook bij een gevulde Optional aan, orElseGet niet; map naar null geeft Optional.empty; flatMap naar null en Optional.of(null) geven een NPE; orElseThrow() en get() gooien NoSuchElementException: No value present; Optional is niet Serializable. Dat javac niets doet met @Nullable en dat de gekwalificeerde plaatsing een compileerfout geeft, is met javac 25 en JSpecify 1.0.0 getest. Het Spring Data-gedrag komt uit de broncode van Spring Data Commons 4.1.1 en de referentiedocumentatie.

Uitgewerkt voorbeeld

Een checkout. Elke shopper moet bij de betaalprovider (PSP) een klant-id hebben, zodat opgeslagen kaarten en terugkerende betalingen aan die klant hangen. De developer schrijft een find-or-create in één expressie. Er staat een unique constraint op psp_customer.shopper_reference.

CheckoutService.java
@Servicepublic class CheckoutService {    private final PspCustomerRepository customers;    private final PaymentRepository payments;    private final PspClient psp;    // constructor-injectie weggelaten+   @Transactional+   public Payment startCheckout(CheckoutCommand cmd) {+       PspCustomer customer = customers.findByShopperReference(cmd.shopperReference())+               .orElse(registerCustomer(cmd));+       return payments.save(Payment.pending(cmd.orderId(), customer.pspCustomerId(), cmd.amount()));+   }++   private PspCustomer registerCustomer(CheckoutCommand cmd) {+       String pspCustomerId = psp.createCustomer(cmd.shopperReference(), cmd.email());   // HTTP+       return customers.save(new PspCustomer(cmd.shopperReference(), pspCustomerId));+   }}

Stap voor stap, voor een klant die vorige week ook al bestelde:

  1. findByShopperReference vindt de klant: Optional[klant].
  2. Voordat orElse wordt aangeroepen, rekent Java het argument uit: registerCustomer(cmd). De PSP maakt een tweede klant aan voor dezelfde shopper.
  3. customers.save(...) wil een tweede rij met dezelfde shopper_reference opslaan. Bij een database-gegenereerd id gebeurt de INSERT direct, anders bij de flush vóór de commit. Hoe dan ook: de unique constraint slaat aan, de transactie rolt terug, de checkout faalt.
  4. Resultaat: elke terugkerende klant kan niet afrekenen, en bij de PSP staat per poging een verweesde klant. Nieuwe klanten merken niets, want daar is de Optional leeg en is het eager uitrekenen toevallig juist.

Zonder unique constraint is het niet beter: dan ontstaan dubbele rijen, en de volgende findByShopperReference met returntype Optional gooit IncorrectResultSizeDataAccessException omdat er meer dan één resultaat is.

Waarom de tests groen zijn: de test "nieuwe klant" gaat door het lege pad. De test "bestaande klant" mockt psp en customers, controleert dat de teruggegeven klant de bestaande is, en dat klopt. Alleen verify(psp, never()).createCustomer(any(), any()), of een integratietest met de constraint, laat het zien.

Oplossingen en hun prijs

A · orElseGet(() -> registerCustomer(cmd))

De kleinste fix en de juiste eerste stap: registerCustomer draait alleen bij een lege Optional. Wat blijft: de HTTP-call naar de PSP zit binnen de transactie (een databaseconnectie staat vast tijdens de call, zie module 1), en twee gelijktijdige eerste checkouts van dezelfde shopper zien allebei een lege Optional en maken allebei een klant aan (check-then-act).

B · Find-or-create idempotent maken aan de bron

Geef de PSP-call een idempotency key (bijv. de shopperReference), zodat een tweede createCustomer dezelfde klant teruggeeft. Laat de unique constraint de race beslissen: verliest jouw INSERT, lees dan de winnaar opnieuw. Prijs: meer code, en een valkuil uit module 1: een DataIntegrityViolationException binnen de checkout-transactie vangen helpt niet, want de transactie is dan al onbruikbaar. Het opnieuw lezen moet buiten die transactie, of je gebruikt een native INSERT … ON CONFLICT DO NOTHING (PostgreSQL).

C · De vraag uit het checkout-pad halen

Maak de PSP-klant aan bij registratie (via een event na de commit) en laat de checkout alleen lezen: .orElseThrow(() -> new CustomerNotOnboardedException(ref)). De checkout heeft dan geen remote side effect meer. Prijs: gastbestellingen hebben een eigen pad nodig, en je moet de situatie afhandelen waarin het event nog niet verwerkt is.

Fix A · CheckoutService.java
        PspCustomer customer = customers.findByShopperReference(cmd.shopperReference())-               .orElse(registerCustomer(cmd));+               .orElseGet(() -> registerCustomer(cmd));   // alleen als de klant nog niet bestaat

Welke methode zegt wat je bedoelt

De meeste Optional-bevindingen in een review zijn geen bugs maar een methode die iets anders zegt dan de auteur bedoelt. Lees de keten als een zin; de juiste methode maakt de bedoeling zichtbaar.

Tweede probleem: de null-cascade, vier varianten

Voor de btw-berekening heb je het land van het factuuradres nodig; gastbestellingen hebben geen Customer, en niet elke klant heeft een factuuradres. Valt het weg, dan geldt het verzendland. Vier manieren om dat op te schrijven:

1 · Cascade van null-checks

String country = null;
if (order.customer() != null
        && order.customer().billingAddress() != null) {
    country = order.customer().billingAddress().countryCode();
}
if (country == null) {
    country = order.shippingCountry();
}

Correct, maar de bedoeling ("factuurland, anders verzendland") moet je reconstrueren. Getters worden twee keer aangeroepen, en een mutable lokale variabele die in twee takken wordt gezet nodigt uit tot fouten bij de volgende wijziging.

2 · Optional-keten

return Optional.ofNullable(order.customer())
        .map(Customer::billingAddress)
        .map(Address::countryCode)
        .orElseGet(order::shippingCountry);

Leest als het pad dat je zoekt, met de fallback aan het eind. Werkt omdat map een null-resultaat omzet in een lege Optional. Hier zou orElse(order.shippingCountry()) ook prima zijn (goedkope getter); orElseGet maakt de keuze alleen expliciet. Prijs: een paar kortlevende objecten, verwaarloosbaar buiten een hot loop; en zodra er logica tussen de stappen komt (loggen, een tweede fallback), wordt een keten snel slechter leesbaar dan variant 3.

3 · Guard clauses in een eigen methode

private static String vatCountry(Order order) {
    Customer customer = order.customer();
    if (customer == null || customer.billingAddress() == null) {
        return order.shippingCountry();
    }
    return customer.billingAddress().countryCode();
}

Even helder als 2, met een naam die de bedoeling draagt, en makkelijk uit te breiden met een extra regel of een debugger-breakpoint. Voor een private helper vaak de beste keuze. Een lambda kan niet returnen uit de omliggende methode en geen checked exception gooien; gewone control flow wel. Maar let op: deze versie is níét equivalent. Heeft een adres geen countryCode, dan vallen 1 en 2 terug op het verzendland en geeft 3 null terug. Bij een herschrijving in review controleer je dus elk null-pad, niet alleen het gelukkige pad.

4 · Het model laten zeggen wat waar is

// Order.java, package is @NullMarked
public String vatCountry() {
    return billingAddress()          // Optional<Address>
            .map(Address::countryCode)
            .orElse(shippingCountry);
}

De echte vraag van een senior: waarom mag het hier null zijn? Als Order zelf weet hoe het btw-land bepaald wordt, schrijft geen enkele aanroeper de cascade nog. Velden blijven @Nullable, de publieke getter geeft een Optional. Prijs: een wijziging in het domeinmodel; niet altijd binnen de scope van de PR, wel een goede suggestion.

In een review is variant 1 geen fout, maar een nit of minor afhankelijk van hoe vaak dit patroon terugkomt. Stel 2 of 3 voor, en noem 4 als de cascade op meer plekken staat: dan is het een modelprobleem, geen stijlprobleem.

Wanneer het géén probleem is

  • orElse met een goedkope, pure expressie. orElse(BigDecimal.ZERO), orElse(List.of()), orElse(merchant.defaultCurrency()) op een gewone getter. Het argument wordt uitgerekend, maar dat kost niets en verandert niets. orElseGet eisen is hier ruis. Ook orElse(null) is prima op de grens naar een @Nullable-veld of een API die null verwacht.
  • Een simpele if (x == null) return …; in een private methode. Optional is geen verplichting. Wie een guard clause vervangt door Optional.ofNullable(x).ifPresent(...) maakt de code langer en de control flow onduidelijker.
  • Optional als parameter op een frameworkgrens. Spring MVC ondersteunt @RequestParam Optional<String> status. Dat is de grens waar afwezigheid binnenkomt; een @Nullable String is daar even goed. Het bezwaar tegen Optional-parameters geldt voor je eigen interne API's, waar elke aanroeper Optional.empty() of Optional.of(...) moet gaan bouwen.
  • isEmpty() + vroege return, gevolgd door orElseThrow(). Als de lege tak meerdere regels werk doet (loggen, metric, ander resultaat), is if (found.isEmpty()) { …; return …; } leesbaarder dan dezelfde logica in een lambda. Dat is geen isPresent/get-antipatroon; het antipatroon is if (opt.isPresent()) return opt.get().x(); else return y;, wat gewoon map(…).orElse(y) is.
  • Kaal orElseThrow() waar afwezigheid onmogelijk is. Bijvoorbeeld direct na een save in dezelfde transactie, of op stream.max(...) over een lijst waarvan je net hebt gecontroleerd dat hij niet leeg is. Een eigen exception zou daar een situatie beschrijven die niet bestaat.

Zwaarte: blocker als het argument van orElse een side effect heeft dat geld, data of een externe partij raakt (save, HTTP, bericht), of als Optional.of op een reëel null-pad in een betaalflow staat · major bij een NPE- of kostenrisico zonder datagevolg (orElse(dureQuery()) op een hot path, Optional.of op een nullable veld in een leespad) · minor voor ontwerpkeuzes die de aanroeper belasten (Optional<List>, Optional-parameter of -veld in eigen code, kaal orElseThrow() op een API-grens) · nit voor isPresent/get en cascades die correct zijn maar beter kunnen · laat gaan bij orElse met een constante.

Zo schrijf je het op

Zwak

Gebruik orElseGet i.p.v. orElse, dat is beter voor performance.

Klinkt als een micro-optimalisatie. De auteur denkt "een paar nanoseconden" en klikt op resolve, terwijl het echte probleem een dubbel PSP-account en een kapotte checkout is.

Sterk

issue (blocking) registerCustomer(cmd) staat als argument van orElse en wordt daarom áltijd uitgevoerd, ook als de klant al bestaat: Java rekent het argument uit voordat orElse kijkt of de Optional gevuld is.

Gevolg: voor elke terugkerende klant een extra klant bij de PSP, en een tweede INSERT op shopper_reference die op de unique constraint stukloopt. Terugkerende klanten kunnen niet afrekenen.

Voorstel: .orElseGet(() -> registerCustomer(cmd)), plus een test die verify(psp, never()).createCustomer(...) doet voor een bestaande klant. Los daarvan: zit de PSP-call bewust binnen de transactie?

Antwoordsleutel tonen

Regels 13–14 (met 22–26) blocker De idempotency die deze PR belooft, werkt precies niet bij een retry. newRefund(cmd) is het argument van orElse en draait dus ook als de refund al bestaat. Bij een retry van een volledige refund ziet reserveRefund een restbedrag van 0 en gooit RefundNotAllowedException: de client krijgt een fout op een refund die gelukt is. Bij een retry van een gedeeltelijke refund wordt het bedrag nog eens gereserveerd (30 wordt 60) en komt er een tweede REQUESTED-rij bij met dezelfde key; met een unique constraint op de key faalt de retry, zonder constraint gooit de volgende findByIdempotencyKey een IncorrectResultSizeDataAccessException. Fix: .orElseGet(() -> newRefund(cmd)).

Regels 11 en 16 blocker Uit module 1. Remote call binnen de transactie. De connectie staat 200–2000 ms vast, en als er ná regel 16 iets faalt, rolt de transactie terug terwijl de PSP het geld al terugstort. Dat gebeurt hier echt, zie regel 43. Na de rollback bestaat de refund niet meer; de retry van de client vindt dus niets, maakt een refund met een nieuw id aan, en stuurt dat als nieuwe idempotency key naar de PSP: dubbele refund. Voorstel: transactie 1 legt de refund vast als REQUESTED, de PSP-call gebeurt daarna buiten een transactie, transactie 2 zet hem op SUBMITTED.

Regel 43 major, met regel 16 een blocker. getReasonCode() is @Nullable, en Optional.of(null) gooit een NPE. Elke refund zonder reden faalt dus in toView, ná de PSP-call; en elke betaling met zo'n refund geeft een 500 op het overzicht. Optional.ofNullable lost het op; map vangt daarna ook een onbekende code af, want reasonCatalog.label die null teruggeeft levert een lege Optional. Les voor de review: Optional.of op een getter is een bewering; check of die getter non-null is.

Regel 23 minor Kaal orElseThrow() op een API-pad. Een onbekend paymentId wordt een NoSuchElementException: No value present: zonder id in de log, en een 500 in plaats van een 404, tenzij iemand een globale handler voor NoSuchElementException heeft (die dan ook echte bugs als 404 maskeert). Voorstel: .orElseThrow(() -> new PaymentNotFoundException(cmd.paymentId())) met een ProblemDetail-mapping.

Regels 29–35 en 51–53 minor Optional<List> geeft "geen refunds" twee representaties: een lege Optional, en (in theorie) een Optional met een lege lijst. Elke aanroeper moet beide kennen. Het gevolg is al zichtbaar in de controller: een bestaande betaling zonder refunds geeft 404, en een client kan niet meer onderscheiden tussen "betaling bestaat niet" en "nog geen refunds". Herschrijving:

public List<RefundView> refundsFor(UUID paymentId) {
    return refunds.findByPaymentIdOrderByCreatedAtDesc(paymentId).stream()
            .map(this::toView)
            .toList();
}

Waarom dit beter is, en niet alleen korter: één pad in plaats van twee, een lege lijst is gewoon een geldig antwoord (200 []), en als "betaling bestaat niet" een 404 moet zijn, wordt dat een expliciete check op de betaling in plaats van een bijeffect van een lege lijst. Stream.toList() is onwijzigbaar, wat bij een view ook de bedoeling is.

Regel 38 geen probleem De afleider. Ja, reasonCatalog.fallbackLabel() wordt altijd uitgerekend, ook als er een label is. Maar het is een goedkope getter op een in-memory object zonder side effects: het resultaat wordt weggegooid en er gebeurt verder niets. Een comment "gebruik orElseGet" is hier hooguit een nit, en wie hem plaatst terwijl regel 14 blijft staan, heeft het verschil niet begrepen. Hetzelfde geldt voor regel 53.

Controlevragen

Beantwoord elke vraag eerst zelf, in één of twee zinnen, voordat je het antwoord opent. Het label laat zien bij welk leerdoel de vraag hoort; lukt een vraag niet, lees dan dat deel van de module nog eens.

  1. Vraag 1Doel 2 · voorspellen

    Een PR voegt een cache toe voor wisselkoersen. fxProvider.fetchRate is een HTTP-call van zo'n 80 ms. In de loadtest zijn alle 1000 requests cache hits.

    BigDecimal rate = rateCache.get(currencyPair)          // Optional<BigDecimal>
        .orElse(fxProvider.fetchRate(currencyPair));

    Hoeveel HTTP-calls doet deze code in de loadtest?

    Antwoord tonen

    1000: de cache bespaart niets, elke request betaalt nog steeds 80 ms.

    Waarom

    • fetchRate(...) is het argument van orElse en wordt uitgerekend vóór de aanroep, of de cache nu iets heeft of niet.
    • Het resultaat wordt bij een hit weggegooid, dus functioneel lijkt alles te kloppen. Alleen de latency en de call-count bij de provider verraden het.

    In de review

    issue: fetchRate staat in orElse en draait dus ook bij een cache hit; de cache spaart geen enkele call. Gebruik .orElseGet(() -> fxProvider.fetchRate(currencyPair)). Een test die het aantal calls naar de provider telt, had dit gevangen.

  2. Vraag 2Doel 1 · herkennen

    Een betaling die nog niet gecaptured is, heeft capturedAt == null. Twee varianten om er een Optional<Instant> van te maken:

    A · map

    Optional.of(payment)
        .map(Payment::getCapturedAt)

    B · of

    Optional.of(payment.getCapturedAt())

    Wat geven A en B voor een betaling die nog niet gecaptured is?

    Antwoord tonen

    A geeft Optional.empty(); B gooit een NullPointerException.

    Waarom

    • map pakt het resultaat in met ofNullable; een null-resultaat wordt een lege Optional.
    • Optional.of eist een niet-null waarde. Het juiste alternatief voor B is Optional.ofNullable(payment.getCapturedAt()).

    Let op

    • Bij flatMap is het andersom: geeft de functie null terug in plaats van een Optional, dan krijg je wél een NPE.
  3. Vraag 3Doel 3 · kiezen en verdedigen

    Een batchjob laadt de betalingen bij een lijst van 500 ids. payments is een Spring Data ListCrudRepository. Drie varianten uit drie PR's:

    // A
ids.stream().map(payments::findById)
        .filter(Optional::isPresent).map(Optional::get).toList();
// B
ids.stream().map(payments::findById)
        .flatMap(Optional::stream).toList();
// C
payments.findAllById(ids);

    Welke keur je goed, en wat schrijf je bij de andere twee?

    Antwoord tonen

    C: één query in plaats van 500. B is de nette vorm van A, maar heeft hetzelfde kostenprobleem.

    Waarom

    • A en B doen elk een findById per id: 500 roundtrips naar de database. De stream-vorm verbergt dat.
    • Als het om lookups in het geheugen ging, was B de beste schrijfwijze: flatMap(Optional::stream) zegt in één stap "neem de aanwezige waarden", waar A het in twee stappen met een get() doet.
    • findAllById doet één query (IN-clause). De volgorde van het resultaat is niet gegarandeerd.

    Let op

    • Alle drie laten ontbrekende ids stil weg. Is een ontbrekende betaling in deze batch een fout, vergelijk dan het aantal resultaten met het aantal ids en meld welke ontbreken.
  4. Vraag 4Doel 4 · kiezen

    Een JPA-entity in een @NullMarked package krijgt een nieuw veld. Twee voorstellen:

    A · Optional-veld

    private Optional<Instant> settledAt
        = Optional.empty();

public Optional<Instant> settledAt() {
    return settledAt;
}

    B · @Nullable-veld

    private @Nullable Instant settledAt;

public Optional<Instant> settledAt() {
    return Optional.ofNullable(settledAt);
}

    Welke kies je, en waarom?

    Antwoord tonen

    B: nullable veld van binnen, Optional alleen als returntype naar buiten.

    Waarom

    • De JPA-specificatie noemt Optional niet als attribuuttype. Reken er niet op dat je provider het zonder converter mapt; de gangbare vorm is B.
    • Optional is niet Serializable; een entity die in een sessie of cache wordt geserialiseerd, faalt met NotSerializableException.
    • Het veld in A kan alsnog null worden (een constructor of mapper die het overslaat), en dan geeft de getter null terug waar een Optional beloofd is.
    • B geeft dezelfde API naar buiten, en @Nullable laat NullAway of de IDE controleren dat code binnen de klasse het veld niet ongecontroleerd gebruikt.
  5. Vraag 5Doel 4 · zwaarte en comment

    Spring Boot 4, Spring Data 4. De repository staat in een package met @NullMarked in package-info.java. Een PR "vereenvoudigt" de finder:

    // PspCustomerRepository
PspCustomer findByShopperReference(String ref);

// CheckoutService
PspCustomer customer = customers.findByShopperReference(ref);
if (customer == null) {
    customer = registerCustomer(cmd);
}

    Wat gebeurt er bij de eerste checkout van een nieuwe shopper, en welke zwaarte geef je?

    Antwoord tonen

    blocker: de finder gooit EmptyResultDataAccessException, de null-check wordt nooit bereikt, en nieuwe klanten kunnen niet afrekenen.

    Waarom

    • In een @NullMarked package is het returntype PspCustomer non-null. Spring Data 4 voegt een interceptor toe die dat tijdens runtime afdwingt: geen resultaat betekent een exception, geen null.
    • De if (customer == null) is daardoor dode code. Een unit-test met een gemockte repository die null teruggeeft, is groen; alleen een test tegen de echte repository laat het zien.

    In de review

    issue (blocking): deze package is @NullMarked, dus findByShopperReference zonder @Nullable gooit EmptyResultDataAccessException als de shopper nog niet bestaat; de null-check wordt nooit bereikt. Houd Optional<PspCustomer> met orElseGet(() -> registerCustomer(cmd)), of maak het returntype @Nullable PspCustomer. Kun je er een @DataJpaTest voor de nieuwe-shopper-case bij zetten?
